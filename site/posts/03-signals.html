Signals

Signals are Datastar's client-side state: named values that data-* attributes read and write, with dependency tracking so that changing one value re-runs exactly the bindings that read it. They also ride along on every request. This part covers both halves: what signals do in the browser, and what the server receives.

Parts 1 and 2 had the server push HTML into the page. Some interactions don't need the server at all. Changing a quantity from 1 to 2 should update the displayed total immediately, and a round trip for that would be silly. Other interactions need the browser to tell the server something: which drink, which size, how many. Signals do both jobs. They hold the values the page reacts to, and they are what @get serializes into the datastar parameter.

The draft form

Brew Board's customer configures a drink before adding it to the cart. Here is that form as lesson 3 renders it. Every attribute that starts with data- is Datastar's.

(def initial-signals
  {:drink "latte" :size "medium" :milk "oat" :qty 1 :quote 0 :error ""
   ;; Underscore: the browser keeps these, @get never sends them.
   :_loading false
   :_prices {:base (update-vals menu :base) :size size-delta :milk milk-delta}})

(def estimate-expr
  "($_prices.base[$drink] + ($_prices.size[$size] || 0) + ($_prices.milk[$milk] || 0)) * $qty")

[:div#app {:data-signals (json/generate-string initial-signals)}
 [:div#draft {:data-computed:estimate estimate-expr
              :data-class:busy        "$_loading"}
  [:label "Drink " [:select {:data-bind:drink ""} …]]
  [:label " Size " [:select {:data-bind:size ""} …]]
  [:label " Milk " [:select {:data-bind:milk ""} …]]
  [:label " Qty " [:input {:type "number" :min 1 :max 10 :data-bind:qty ""}]]
  [:p "Browser estimate: " [:span {:data-text "'$' + ($estimate / 100).toFixed(2)"}]]
  [:button {:data-on:click           "@get('/quote')"
            :data-indicator:_loading ""
            :data-attr:disabled      "$_loading"}
   "Ask the server"]
  [:p {:data-show "$quote > 0"}
   "Server quote: " [:strong {:data-text "'$' + ($quote / 100).toFixed(2)"}]]
  [:p.error {:data-show "$error != ''" :data-text "$error"}]
  [:h3 "What @get('/quote') sends (no _ signals)"]
  [:pre {:data-json-signals "{exclude: /(^|\\.)_/}"}]]]

Going through the attributes:

  • data-signals merges an object into the store. Its value is an expression, so JSON works (JSON is a valid JavaScript object literal). A keyed form exists too: data-signals:qty="1". The value is evaluated, so a string needs inner quotes: data-signals:drink="'latte'".
  • data-computed:estimate creates a read-only signal whose value is the expression. It recomputes when something it read changes. One medium oat latte gives (450 + 50 + 60) × 1 = 560 cents.
  • data-bind:qty wires an input to a signal in both directions. The type follows the signal: qty started as the number 1, so typing "2" stores the number 2, not the string. For a select, the binding listens for change. For a number or range input it listens for input, so it updates on every keystroke.
  • data-text, data-show, data-class:busy, data-attr:disabled, and data-json-signals are effects. Each evaluates its expression and writes the result into the element (text content, display: none, a class, an attribute, a JSON dump), and does it again whenever the expression's inputs change.
  • data-on:click runs an expression when the event fires.
  • data-indicator:_loading sets $_loading to true while a request is in flight and back to false after. It only counts requests started by the element it is on. indicator.ts compares the fetch event's element with its own and ignores the rest. Put it on the button that has the data-on:click, or it never turns on. The lesson also declares _loading false up front, because #draft's data-class:busy reads it before the button has been processed.

Why the signals are on a different element

The signals are declared on div#app, and everything that reads them is inside it. That isn't style. Datastar applies an element's data-* attributes in the order they appear in the source (applyEls in engine.ts loops over el.dataset), and it processes elements in document order, parents before children. Hiccup, however, writes attributes sorted by name: {:data-signals … :data-computed:estimate …} comes out as data-computed:estimate="…" data-signals="…". On one element, the computed would be set up before the signals it reads exist. Putting data-signals on an ancestor removes the question: by the time Datastar reaches anything inside #app, the store is populated. Make that a habit. One element declares, its descendants use.

Three rules about names save debugging time. Attribute keys are converted to camelCase, so data-bind:customer-name creates $customerName. In an expression, though, $customer-name means $['customer-name'] (the rewrite rules in engine.ts say so explicitly), which is a different signal. Use camelCase in expressions, and put spaces around minus signs: $qty-1 is the signal qty-1, while $qty - 1 is arithmetic. Second, reading a signal that doesn't exist creates it with the value '', so a typo gives you an empty string instead of an error. Third, a name that starts with an underscore is private to the browser. That's the next section.

What re-runs when a signal changes

Nothing in that markup says "when qty changes, update the total". Datastar works that out by watching what each expression reads. Its store, in engine/signals.ts, follows the alien-signals algorithm (the internal types are named AlienSignal, AlienComputed, and AlienEffect). Simplified, it works like this:

run(effect)
  activeSub = effect                 -- "whoever reads now, reads on my behalf"
  effect.deps = []                   -- dependencies are collected fresh on every run
  effect.fn()                        -- each signal read does: link(signal, activeSub)
  activeSub = previous

write(signal, v)
  if signal.value === v -> return    -- same value: nothing is notified
  signal.value = v
  for each sub of signal.subs
    match sub
      case Computed -> mark dirty; propagate to its subs   -- recomputed lazily, when read
      case Effect   -> queue it
  if not inside a batch -> flush the queue    -- data-on handlers run inside a batch

Two consequences matter for writing pages. A binding re-runs only when a signal it actually read on its last run changes. Since dependencies are collected on every run, a conditional expression can change its own dependencies: $milk ? $_prices.milk[$milk] : 0 reads $_prices.milk only while a milk is set. And writing the value a signal already has does nothing at all, which is why a server can patch the same signals over and over without making the page do work.

One more consequence is less obvious. An effect that reads a computed re-runs only if the computed's value changed. Switch the milk from oat to almond: $estimate has to recompute, because it read $milk, but oat and almond both add 60, so it comes out at 560 again. The estimate's data-text reads only $estimate, so it doesn't run. The store checks whether a dirty computed actually changed before running anything that depends on it.

Try it. Each button writes one signal. Accent marks the write, teal marks what re-ran, and the rest stayed put.

What travels to the server

When the button runs @get('/quote'), the fetch plugin collects the signals it is allowed to send and serializes them. The rule is in fetch.ts: the default filter is include /.*/, exclude /(^|\.)_/. Any signal whose path has a segment that starts with _ stays in the browser. Computed signals are not special. $estimate is a signal like any other, so it is sent.

For the draft above, the request is

GET /quote?datastar=%7B%22drink%22%3A%22latte%22%2C%22size%22%3A%22medium%22…
                                     -- decoded:
{"drink":"latte","size":"medium","milk":"oat","qty":1,"quote":0,"error":"","estimate":560}

The price table under $_prices is not sent, and neither is $_loading. That is the point of the underscore: _prices exists so the browser can show an estimate as you click around, and there is no reason to ship the whole menu back to the server on every request. The lesson's page prints both views live with data-json-signals: everything in the store, and the same filter the request uses. You can override the filter per request with @get('/quote', {filterSignals: {include: /^drink$/}}), but the default is almost always what you want.

Reading signals in Clojure

For GET and DELETE the JSON is in the datastar query parameter. For POST, PUT, and PATCH it is the request body, with Content-Type: application/json. That's the whole contract (it's the ReadSignals table in the ADR):

(defn read-signals
  "Read the signals Datastar sent. GET and DELETE send them as JSON in the datastar query
  parameter; other methods send a JSON body. Return a map with keyword keys."
  [{:keys [request-method query-params body]}]
  (let [raw (if (#{:get :delete} request-method)
              (get query-params "datastar")        ; query-params: ring's wrap-params
              (some-> body slurp))]
    (if (string/blank? raw) {} (json/parse-string raw true))))

And the handler behind "Ask the server". The browser showed a price, but the browser's copy of the menu could be stale, and a modified page could show anything. The server recomputes from its own menu, validates the combination, and answers with signals only:

(defn ->draft
  "Turn signals (strings from the browser) into a draft with keywords."
  [{:keys [drink size milk qty]}]
  {:drink (some-> drink not-empty keyword)
   :size  (some-> size not-empty keyword)
   :milk  (some-> milk not-empty keyword)
   :qty   qty})

(defn quote-response
  "Answer the browser's signals with the server's quote: patch the quote and error signals."
  [signals]
  (let [draft (->draft signals)]
    (sse/sse-response
     (sse/patch-signals (if-let [err (draft-error draft)]
                          {:quote 0 :error err}
                          {:quote (* (price-cents draft) (:qty draft)) :error ""})
                        {}))))

draft-error returns a sentence or nil: "Espresso does not take that milk.", "Quantity must be 1 to 10.", and so on. The router passes (read-signals req) in, so the handler is a function of plain data.

Two medium oat lattes come back as {"quote":1120,"error":""}, in cents. Patch-signals applies it as a merge patch, the effects that read $quote and $error re-run, and nothing else in the page changes. No HTML came over the wire.

When a signal is the wrong tool

The draft form shows the right use. Signals hold the user's in-progress input, and values derived from it for display. The browser can do all of that alone. It's tempting to go further: put the cart in a signal, put the order list in a signal, render everything from signals with data-text and friends, and use the server as a JSON API. That turns Datastar back into the single-page application it was designed to replace, with a worse templating language.

Even the quote flow has a smell. The server computed a price, sent it as a number, and the page has to know where to display it. If the server had rendered the price line as HTML, it could also decide the wording, the currency format, and the "sold out" note. Part 4 makes this a rule, places every piece of Brew Board's state, and builds the drop-down where the decision is least obvious.

A signal is a named reactive value. Bindings re-run only when a signal they read changes value; computed signals recompute lazily. Every signal whose name (or path segment) doesn't start with _ is sent with every request, in the datastar query param for GET/DELETE and as the JSON body otherwise.
