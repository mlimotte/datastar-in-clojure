HTML over the wire

A button says @get('/hello'). The server answers with an event stream that carries HTML. Datastar finds the element with the matching id and patches it in place. That loop is the whole framework. The other six parts are about using it well.

Most web apps built in the last ten years split the work like this: the server sends JSON, and a JavaScript application in the browser turns the JSON into DOM. The application has its own state, its own router, its own build, and its own copy of half the business rules. Datastar splits it differently. The server renders HTML, the same way a server rendered HTML in 2005, and a single script on the page (11.89 KiB, according to the v1.0.4 README) does two small jobs. It reads data-* attributes and wires them to a small reactive store, which is part 3. And it turns server responses into DOM patches, which is this part and the next.

This series is about using Datastar from Clojure without an SDK. Datastar publishes an official Clojure SDK, and it's good. But the wire format is a few dozen lines of string building, and once you've written those lines yourself, nothing the browser does is a mystery. Part 2 writes them. This part writes the smallest version that works.

The page

A Datastar page is ordinary HTML with one script tag. We render it with hiccup:

(def datastar-cdn
  "https://cdn.jsdelivr.net/gh/starfederation/datastar@v1.0.4/bundles/datastar.js")

(defn page []
  (str "<!DOCTYPE html>"
       (h/html
        [:html
         [:head
          [:meta {:charset "utf-8"}]
          [:title "Part 1: HTML over the wire"]
          [:script {:type "module" :src datastar-cdn}]]
         [:body
          [:h1 "HTML over the wire"]
          [:div#greeting "Nobody has said hello yet."]
          [:button {:data-on:click "@get('/hello')"} "Say hello (SSE)"]
          " "
          [:button {:data-on:click "@get('/hello-html')"} "Say hello (text/html)"]]])))

Two attributes do the work. id="greeting" names the element the server will replace. data-on:click="@get('/hello')" tells Datastar: when this button is clicked, evaluate the expression @get('/hello'). The @ marks an action. Datastar rewrites @get('/foo') into a call to its fetch plugin before it evaluates the expression (the rewrite rules are listed in a comment in engine.ts).

Hiccup renders a keyword with a colon in it, :data-on:click, as the attribute name data-on:click. Use single quotes inside the expression. Hiccup escapes them as &apos;, which the browser decodes when it parses the attribute, so view-source looks odd but Datastar sees @get('/hello'). One hiccup trap to know now: never write true as an attribute value. Hiccup renders {:data-bind:drink true} as data-bind:drink="data-bind:drink", and Datastar reads that value. Write "" for an attribute that has no value.

The click, step by step

Here is what happens between the click and the new text. Step through it. Each step is what the browser or the server actually sees.

Three details in that request are easy to miss.

The request always carries signals. The page has no signals yet, but the URL is still /hello?datastar=%7B%7D. For a GET, Datastar serializes the signals it is allowed to send (part 3 covers which ones) as JSON and puts the JSON in a query parameter named datastar. For POST, PUT, and PATCH it sends the same JSON as the request body. With no signals, the JSON is {}.

The request identifies itself. Every Datastar request has the header Datastar-Request: true and Accept: text/event-stream, text/html, application/json. Part 5 uses the first header as a cheap guard on routes that change state.

The response is a stream, even for one event. The server answers with Content-Type: text/event-stream, and the body is one event:

event: datastar-patch-elements
data: elements <div id="greeting"><strong>Hello from the server!</strong> Visit number 1.</div>
                                          -- a blank line ends the event

The event has a type line, then one data: line per line of payload, then a blank line. Each data line starts with a key (elements), a space, and the value. The browser reads the event, parses the HTML, sees that its top-level element has id="greeting", finds the element with that id in the page, and morphs the old element into the new one. Morphing means it changes only what differs. Part 6 relies on that heavily.

The handler

A one-shot SSE response is an ordinary Ring response. The body is the event text, and the browser reads it until the connection closes. We don't need an async server, a channel, or a library for that:

(defn sse-event
  "Format one SSE event: an event line, one data line per entry, then a blank line."
  [event-type data-lines]
  (str "event: " event-type "\n"
       (string/join (map #(str "data: " % "\n") data-lines))
       "\n"))

(defn greeting-html
  "The element the server sends back. Its id tells Datastar where it goes."
  [visits]
  (str (h/html [:div#greeting [:strong "Hello from the server!"] (str " Visit number " visits ".")])))

(defn hello-response
  "A one-shot SSE Ring response that patches #greeting."
  [visits]
  {:status  200
   :headers {"Content-Type"  "text/event-stream"
             "Cache-Control" "no-cache"}
   :body    (sse-event "datastar-patch-elements" [(str "elements " (greeting-html visits))])})

That's the whole server half. The lesson routes with a plain case on [request-method uri], and the /hello branch is (hello-response (swap! visits inc)), which counts clicks so you can see each patch land. (Part 5 swaps the case for reitit, once there are enough routes to need it.) hello-response is a plain function from a number to a response map, so the test calls it directly and checks the string. No server needs to be running.

How Datastar reads the stream. Browsers ship a built-in SSE client, EventSource. Datastar doesn't use it. EventSource can only make GET requests, can't send a request body, and can't set request headers. Datastar calls fetch instead, reads the response body as bytes, splits the bytes into lines, and assembles events itself. The parser in fetch.ts follows the WHATWG event-stream rules: data lines append to the event's data (joined with \n), event, id, and retry set fields, and an empty line dispatches the event. Datastar then ignores any event whose type doesn't start with datastar. So a POST can answer with a stream, and so can a DELETE. Part 5 depends on that.

Not every response has to be a stream

Datastar looks at the response's Content-Type before it decides what to do. The request said it accepts three types, and the status code matters too: only a 200 is applied.

responsewhat Datastar does
text/event-streamparses events until EOF and applies each one
text/htmltreats the whole body as one patch-elements event. Options come from response headers datastar-selector, datastar-mode, …
application/jsontreats the body as one patch-signals event
204 No Contentnothing. It doesn't retry, and no error appears.
any status but 200the body is ignored. A 4xx or 5xx also fires a datastar-fetch error event you can listen for; the page itself doesn't change.

So the lesson's second button, @get('/hello-html'), gets the same patch as plain HTML:

(defn hello-html-response
  "The same patch as a text/html response. Datastar morphs each top-level element by id."
  [visits]
  {:status  200
   :headers {"Content-Type" "text/html"}
   :body    (greeting-html visits)})

The browser ends up in the same state. Why bother with SSE at all? Because one HTML response can carry one patch, and one event stream can carry many, of different kinds, over time. Part 3 sends an element patch and a signal patch in the same response. Part 6 holds one stream open for the life of the page. Use text/html when the answer really is one element; use the stream for everything else. The rest of this series mostly uses the stream, because the same writer then covers every case.

What the browser didn't do

Look at the list of things that didn't happen during that click. No JSON was parsed into a model. No component tree re-rendered. No client-side router changed. The browser had no idea what a "greeting" is. It had an id and some HTML. Everything that knows about greetings (and later about drinks, carts, and orders) lives in one place, the Clojure process.

That has a consequence that this series comes back to in its last part. Anything that can load a web page and run fetch can host this UI unchanged, and the server decides what that UI looks like on every response. Keep that in mind when you get to part 7.

It also has a cost, and it's fair to name it now. Every interaction that needs the server's knowledge pays a round trip. A drop-down whose options depend on stock (part 4) can't fill itself without asking. Part 3 shows how Datastar handles the interactions that don't need the server at all (a counter, a computed total, showing and hiding things) entirely in the browser, with signals.

A Datastar interaction is a request from a data-on expression and a response the browser applies as patches. The response is usually text/event-stream: event: datastar-patch-elements, one data: elements … line per line of HTML, a blank line. Datastar finds the target by id and morphs it. A one-shot stream is just a Ring response with a string body.
