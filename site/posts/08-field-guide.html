Field guide: practices and trade-offs

Advanced. Parts 1–7 built Brew Board one way. This part steps back. First, two practices that decide where code goes: the decision ladder, and how navigation and the URL work when Datastar has no history API. Then six places where a reasonable app could choose the other way, each with what it costs and what Brew Board chose.

Most of this part came from setting the course next to a production Datastar codebase and asking, rule by rule, which of its rules were about that app and which were about Datastar. Some of what survived is already in the earlier parts:

  • the server renders error messages as HTML (parts 3–7)
  • the browser never computes a price (part 3)
  • a tab gets its own id (part 6)
  • signal count must not grow with the data (part 4)

What's left is bigger than a tip box, and it's here.

There are no exercises in this part. Lesson 8 is a demo: it answers the same read two ways, sends the same change two ways, and races two search requests. It prints the bytes so the numbers below are measured, not estimated.

The decision ladder

Every interaction on a page needs somewhere to live. The ladder is the order in which to try homes:

rungmechanismwho owns the stateBrew Board example
1server round-tripthe serversize options, the cart, every order status
2native HTMLthe browser<details>, popover, <form method="get">, maxlength
3CSSnobody: it's derived from the DOM:hover, :empty, :has()
4Datastar attributessignals, in this tabdata-bind on the draft, data-indicator
5custom JavaScriptyou, line by linepart 7's BrewShell.post bridge shim

Try the rungs top to bottom and stop at the first that does the job. When you skip a rung for a reason a reader wouldn't guess, leave a one-line comment saying why: "data-init focus, not autofocus: autofocus doesn't fire again after a morph."

The order isn't about taste. Each rung down adds state that you own and have to keep correct:

  • Rung 1 keeps everything in one process, one language, and one test suite.
  • Rung 2 hands the state to the browser, which also gives you keyboard handling, accessibility and Back/Forward for free.
  • Rung 3 has no state at all.
  • Rung 4 is declarative, but every data-* expression is JavaScript living in an attribute, and anything it computes is a client-side copy of something.
  • Rung 5 is yours entirely.

Rung 1 is first because Datastar makes it cheap. It is not "always ask the server": a request per keystroke to learn something the browser already knows is a reason to skip it. The rule from part 3 still holds on rung 4: an expression may count, format, toggle and focus, but it never computes a business value. Pick an interaction and step down the ladder:

Native HTML inside a re-rendered region

Rung 2 has one catch in a whole-view app. When the user opens a <details>, the browser adds an open attribute to it. The server's next render doesn't have that attribute, because the server doesn't know the user opened anything. The morph copies attributes from the new HTML and removes the ones the new HTML lacks (morphNode in patchElements.ts), so the panel snaps shut on every update.

The fix is one attribute on the server-rendered element:

[:details#receipt {:data-preserve-attr "open"}
 [:summary "Receipt"]
 [:p "Medium oat latte, $5.60"]]

data-preserve-attr is read from the new HTML. It lists attributes the morph must neither set nor remove, separated by spaces.

Lesson 8's page has two receipts side by side, one with data-preserve-attr and one without. Open both, click "Re-render receipts", and only the first stays open. A modal <dialog> has the same issue, because showModal() sets open too. A popover's open state is not an attribute, so the morph doesn't see it at all.

CSS before data-show

Parts 3–7 render error messages as server HTML. The leftover question is how to hide the empty element so it takes no space. That's rung 3, not rung 4:

#draft-error:empty { display: none; }                /* no message, no box */
#cart:has(li) .empty-hint { display: none; }          /* "Add a drink to start" */

:empty matches only an element with no children at all, not even whitespace. Hiccup renders [:p#draft-error] as <p id="draft-error"></p>, which matches.

Custom JS, enumerated

Some things only rung 5 can do. Datastar has no attribute that talks to a native shell, and no history API (next section). Keep what's left in one glue script per page, and list every item in its header with the reason the lower rungs failed:

// brew-glue.js: each item was tried against the ladder first.
// 1. BrewShell.post (part 7): forwards bridge messages to WKWebView or the Android
//    JavascriptInterface. No HTML, CSS or Datastar attribute reaches native code.
// 2. History sync: mirrors #board-orders[data-query] into history.pushState.
//    Datastar has no history primitive.

The list is the point. A glue file that has to justify each entry stays at two or three entries. One that doesn't turns into a second front end.

Navigation and the URL

Datastar doesn't touch history: there is no pushState or popstate anywhere in its library/src. Use it inside a page, and use the browser between pages:

  • Between pages, use real links and full page loads. Brew Board's /, /board and /orders/:id are pages, and an <a href> to one of them is a plain link. Back, bookmarks, "open in new tab" and part 7's shell all work because of that: the shell turns a link into a native screen push using the path configuration the server serves.
  • View state worth bookmarking goes in the URL. That means filters, a page number, a selected tab. The first choice is rung 2, a <form method="get">. The filter becomes a query string, the server renders the page for that query, and Back works with no code. The cost is a full page load per change.

When a full load is too slow and you update in place, the URL needs help. The server stamps the canonical query string it rendered on an element, a few lines of glue mirror it into pushState, and Back is handled declaratively:

<section id="board-view" data-signals="{status: 'all'}"
         data-on:popstate__window="$status = new URLSearchParams(location.search).get('status') ?? 'all';
                                   @get('/board/orders')">
  <ul id="board-orders" data-query="?status=making">…</ul>
</section>

A sketch, not lesson code. __window attaches the listener to window, where popstate fires. The view-state signal lives on a wrapper outside the patched list, so a re-render never resets it.

A related trap: URLs baked into server-rendered attributes, like a pager's @get('/board/orders?page=2'). Under a whole-view re-render they are fine, because the pager is re-rendered with the view every time. Under targeted patches, a pager outside the patched region keeps the URL it was first rendered with, and "next page" goes to the same page forever. With targeted patches, keep view state in signals on a stable wrapper, have each control change a signal, and send every refresh through one fetch path.

htmx builds history in. hx-push-url pushes the URL, a snapshot of the page's history element is saved in sessionStorage, and its popstate handler restores the snapshot. On a cache miss it re-fetches the URL with an HX-History-Restore-Request header. Datastar left all of this out. In an app where the server owns the view, Back asking the server again is usually what you want, and the glue above is about ten lines. Part 7's native shell is the third model: the server publishes navigation rules, and the shell owns the stack.

Six trade-offs

For each of the six: when to pick each side, what it costs, and what Brew Board chose.

1. Whole-view re-render or targeted patches

Part 6 re-renders the whole #app on every change and lets the morph keep what didn't change. The alternative is to send only the elements a change touched. Lesson 8 sends "advance order #3" both ways on a four-row board: the whole board is 316 bytes on the wire, the targeted patch of #order-3 is 114 bytes. The more interesting difference is what happens on screen.

The morph keeps identity: patchElements.ts finds an element with a matching id and moves it (moveBefore where the browser has it, insertBefore otherwise) instead of rebuilding it. So listeners and the element's own state survive a re-sort. Position on screen does not survive. If the server's sort order changes, rows move, and whatever was under the user's pointer can change.

whole viewtargeted patches
renderersone view function; the page GET and the stream share itone per patched region; share them with the page or they drift
derived contentcounts, sorts and headings are always rightstale unless you also patch every region the change touches
server knowledgeonly "something changed"exactly which elements changed
bytesthe whole view; part 6 measured 39–44 bytes per update through a shared deflate streamsmall without compression
content movingyes, when sort order changesno; that's also why the sort goes stale
reconnectsame code path: render the viewneeds a full render anyway

Pick whole view by default, especially for live views with several viewers. It is the one approach where forgetting a region is impossible. Pick targeted patches for a large editable grid where a save shouldn't move the row being edited, or when one region updates much more often than the rest. Even then, the page and the fragment endpoint must call the same render function.

To keep whole-view rendering but stop rows jumping:

  • Sort by something that doesn't change while people work, such as order id or arrival time, and show status with a style instead.
  • Put each status in its own section, so an order leaves one list and joins another.
  • Pass useViewTransition (part 2) so the browser animates the move instead of teleporting it.

Brew Board chose: whole view, sorted by status. That is fine for a barista who watches the board, and a known hazard for one who clicks fast.

2. text/html or SSE for reads

Part 1 showed that Datastar accepts a plain text/html response and patches its top-level elements by id. Lesson 8 answers the same menu read both ways: 232 bytes of HTML, or 280 bytes as one SSE event. Patch options travel in response headers (datastar-selector, datastar-mode, …), so even an append works without SSE:

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
datastar-selector: #menu-card
datastar-mode: append

<li>Seasonal: Pumpkin Latte</li>

Pick text/html for reads that return one element. The handler is an ordinary Ring handler, you can open the URL in a browser tab and see the fragment, and there's no event framing to get wrong. Pick SSE when one response must carry several patches, element and signal patches together (part 4's drop-down sends both), or a stream held open over time.

Brew Board chose: SSE everywhere, so one writer from part 2 covers every case. A production codebase commonly splits it instead: reads are text/html, and writes that need several patches are SSE. Neither is wrong.

3. HTML or signals for values the server sends

The server can put a value on screen in two ways: render it into HTML, or patch-signals it into a signal that a data-text displays. They look the same to the user, but they behave differently over time:

  • HTML is replaced by the next render. There is nothing to keep in sync.
  • A signal is a client-side copy of server state, and it stays until someone overwrites it. Under a whole-view re-render, an element that displays a signal also competes with the morph.

That is why parts 3–7 moved prices and error messages into HTML.

Use patch-signals when the server writes into something the client owns. Part 4's drop-down resets $size because the user's draft is held in signals and the old size isn't valid for the new drink. Clearing an input after a successful command is the same case. Use HTML for everything the user only reads.

4. Request ordering and cancellation

Two requests in flight can finish in either order. Datastar has one built-in rule for this, in fetch.ts: a module-level map holds one AbortController per method and URL, and a new request aborts the one in flight under the same key (default requestCancellation: 'auto'). The key is the URL string exactly as written in the action, before Datastar appends its datastar parameter. So two @get('/search') calls cancel each other, while @get('/search?q=la') and @get('/search?q=lat') don't.

In a real Chrome run against lesson 8's page, typing "lat" quickly into the per-query-URL box left the results showing an earlier, shorter query. The other two boxes showed "lat". The options:

The table's choices can be combined: debounce for load, plus one of the first two for correctness. requestCancellation: 'disabled' exists for the rare case where you want both answers. Brew Board chose: it has no search box, and its commands are different URLs that shouldn't cancel each other. Part 4's searchable-combobox stretch exercise should use one URL.

5. data-indicator or a hand-managed flag

A common first attempt at "disable Save while saving" is $saving = true; @post('/save'), with the server clearing $saving in its response. If the network drops, no response arrives, and the page stays locked until reload. data-indicator counts the element's in-flight fetches, and fetch.ts dispatches the finished event in a finally block, so the count comes down after success, an error status, or a dropped connection. The one catch, from part 3: it only counts fetches started from the element that carries it.

Brew Board chose: data-indicator. We found no case where the flag is better.

6. Per-tab or per-browser identity

Part 6 found the bug: a cookie identifies a browser, every tab shares it, so per-cookie state shows up in every tab. The split Brew Board settled on:

  • Per browser (the sid cookie): things that belong to the person. That is the cart, the orders, and the registered push device.
  • Per tab (a tabid signal): things that belong to one view. That is the draft being configured and the error message about it.

The tab id is seeded once with data-signals:tabid__ifmissing="crypto.randomUUID()" on <body>, outside every morph target. It is fresh on each full load, stable across re-renders, and (like every non-_ signal) sent with every request. crypto.randomUUID() needs a secure context: https, or localhost during development.

Put each interaction on the highest rung of the ladder that can do it (server, native HTML, CSS, Datastar attributes, custom JS), and justify every line of glue. Navigate with links and full loads, and keep bookmarkable state in the URL. The remaining choices are trade-offs, not rules:

  • whole-view rendering trades bytes and moving content for one renderer that can't go stale
  • text/html is enough for one-element reads
  • the server sends HTML for values the user reads, and signals only for what the client owns
  • the URL string you write decides which requests cancel each other
  • data-indicator always comes down after a request
  • per-tab state needs a tab id
