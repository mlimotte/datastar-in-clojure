Field guide: practices and trade-offs

Advanced. Parts 1–7 built Brew Board one way: our way. This part is where we put the tools down, step back from the workbench, and squint at what we made. First come two practices that decide where your code goes: the decision ladder, and how navigation and the URL work when Datastar flat-out refuses to have a history API. Then come six places where a perfectly reasonable app could have gone the other way, each with what it costs and what Brew Board chose. No sacred cows. Well, maybe one.

Here's where most of this part came from. We set the course down next to a production Datastar codebase and went through it rule by rule, asking one rude question of each: are you about that app, or are you about Datastar? A lot of rules turned out to be local customs. Some survived the interrogation, and you've already met those in the earlier parts:

  • the server renders error messages as HTML (parts 3–7)
  • the browser never computes a price (part 3)
  • a tab gets its own id (part 6)
  • signal count must not grow with the data (part 4)

What's left over is too big to stuff into a tip box, so it lives here.

Fair warning: there are no exercises in this part. Lesson 8 is a demo, and a slightly obsessive one. It answers the same read two ways, sends the same change two ways, and races two search requests against each other like slot cars. It prints the bytes, too, so every number below is measured, not made up over coffee.

The decision ladder

Every interaction on a page has to live somewhere. It's like a stray cat: it will move in whether you planned for it or not, so you might as well pick the house. The ladder is the order in which to try houses:

rungmechanismwho owns the stateBrew Board example
1server round-tripthe serversize options, the cart, every order status
2native HTMLthe browser<details>, popover, <form method="get">, maxlength
3CSSnobody: it's derived from the DOM:hover, :empty, :has()
4Datastar attributessignals, in this tabdata-bind on the draft, data-indicator
5custom JavaScriptyou, line by linepart 7's BrewShell.post bridge shim

The rule is dead simple: try the rungs top to bottom and stop at the first one that does the job. The only extra bit of discipline is this. When you skip a rung for a reason the next reader wouldn't guess, leave them a one-line comment saying why. Something like: "data-init focus, not autofocus: autofocus doesn't fire again after a morph." Future-you will want to send present-you a fruit basket.

Now, you might think the order is just my taste talking. It isn't. Each rung you climb down adds state that you own and have to keep correct, forever, with your own two hands:

  • Rung 1 keeps everything in one process, one language, and one test suite. Lovely.
  • Rung 2 hands the state to the browser, and the browser throws in keyboard handling, accessibility and Back/Forward for free, like a dealership that keeps adding floor mats.
  • Rung 3 has no state at all. You can't get state wrong if there isn't any.
  • Rung 4 is declarative, sure, but don't kid yourself: every data-* expression is JavaScript living in an attribute, and anything it computes is a client-side copy of something.
  • Rung 5 is yours entirely. Every bug in it has your name on it.

Rung 1 sits at the top because Datastar makes it cheap. That does not mean "always ask the server." Firing off a request per keystroke to learn something the browser already knows is a perfectly good reason to skip it. And the rule from part 3 still holds down on rung 4: an expression may count, format, toggle and focus, but it never, ever computes a business value. Go ahead, pick an interaction and walk it down the ladder:

Native HTML inside a re-rendered region

Rung 2 has exactly one catch in a whole-view app, and it's a sneaky one. When the user opens a <details>, the browser quietly adds an open attribute to it. The server's next render doesn't have that attribute, because the server has no idea the user opened anything. Why would it? The morph copies attributes from the new HTML and removes the ones the new HTML lacks (morphNode in patchElements.ts). So the panel snaps shut on every update, like a clam that's been poked.

The fix is one attribute on the server-rendered element. One:

[:details#receipt {:data-preserve-attr "open"}
 [:summary "Receipt"]
 [:p "Medium oat latte, $5.60"]]

data-preserve-attr is read from the new HTML. It lists, separated by spaces, the attributes the morph must keep its hands off: neither set them nor remove them.

You can watch this happen. Lesson 8's page has two receipts side by side, one with data-preserve-attr and one without. Open both, click "Re-render receipts", and only the first one stays open. The other one slams shut. A modal <dialog> has the same problem, because showModal() sets open too. A popover, on the other hand, keeps its open state somewhere that isn't an attribute, so the morph never even sees it. Lucky popover.

CSS before data-show

Parts 3–7 render error messages as server HTML, which settles the hard part. The leftover question is a humble one: how do you hide the empty element so it doesn't take up space? Your fingers will reach for rung 4. Slap them. That's a rung 3 job:

#draft-error:empty { display: none; }                /* no message, no box */
#cart:has(li) .empty-hint { display: none; }          /* "Add a drink to start" */

One gotcha: :empty matches only an element with no children at all, not even whitespace. Happily, Hiccup renders [:p#draft-error] as <p id="draft-error"></p>, which matches.

Custom JS, enumerated

Some things only rung 5 can do, and there's no shame in that. Datastar has no attribute that talks to a native shell, and no history API (more on that in a minute). So keep whatever's left in one glue script per page, and, this is the important part, list every item in its header along with the reason the lower rungs failed:

// brew-glue.js: each item was tried against the ladder first.
// 1. BrewShell.post (part 7): forwards bridge messages to WKWebView or the Android
//    JavascriptInterface. No HTML, CSS or Datastar attribute reaches native code.
// 2. History sync: mirrors #board-orders[data-query] into history.pushState.
//    Datastar has no history primitive.

The list is the whole point. A glue file that has to justify each entry stays at two or three entries, because justifying things is tedious and people avoid tedium. A glue file that doesn't have to justify anything grows, slowly and then all at once, into a second front end. And then you're right back where part 7 started, with two crews painting one fence.

Navigation and the URL (or: Datastar does not do history)

Datastar doesn't touch history. At all. Go look: there is no pushState or popstate anywhere in its library/src. Some people find this alarming. I find it refreshing. The deal is: use Datastar inside a page, and use the browser between pages. The browser has been doing pages for thirty-odd years. It's pretty good at it.

  • Between pages, use real links and full page loads. Brew Board's /, /board and /orders/:id are pages, and an <a href> to one of them is a plain old link. Back, bookmarks, "open in new tab" and part 7's shell all work because of that: the shell turns a link into a native screen push using the path configuration the server serves. Break the links and you break all four.
  • View state worth bookmarking goes in the URL. That means filters, a page number, a selected tab. Your first choice is rung 2, a humble <form method="get">. The filter becomes a query string, the server renders the page for that query, and Back works with zero code. The cost is a full page load per change, which is a real cost, but often a smaller one than you'd think.

When a full load really is too slow and you update in place, the URL needs a little help. The server stamps the canonical query string it rendered onto an element, a few lines of glue mirror it into pushState, and Back is handled declaratively:

<section id="board-view" data-signals="{status: 'all'}"
         data-on:popstate__window="$status = new URLSearchParams(location.search).get('status') ?? 'all';
                                   @get('/board/orders')">
  <ul id="board-orders" data-query="?status=making">…</ul>
</section>

A sketch, not lesson code. __window attaches the listener to window, which is where popstate fires. Notice the view-state signal lives on a wrapper outside the patched list, so a re-render can never reset it out from under you.

Now here's a related trap, and it's a nasty one: URLs baked into server-rendered attributes, like a pager's @get('/board/orders?page=2'). Under a whole-view re-render they're fine, because the pager gets re-rendered along with the view every time. Under targeted patches, though, a pager outside the patched region keeps whatever URL it was first rendered with. So "next page" goes to the same page. Forever. It's Groundhog Day with a pagination widget. With targeted patches, keep view state in signals on a stable wrapper, have each control change a signal, and send every refresh through one fetch path.

htmx went the other way and built history right in. hx-push-url pushes the URL, a snapshot of the page's history element gets saved in sessionStorage, and its popstate handler restores the snapshot. On a cache miss it re-fetches the URL with an HX-History-Restore-Request header. Datastar left all of that out, on purpose. In an app where the server owns the view, having Back just ask the server again is usually exactly what you want, and the glue above is about ten lines. And part 7's native shell is a third model entirely: the server publishes navigation rules, and the shell owns the stack.

Six trade-offs

Here's where we stop handing down rules and start arguing. For each of the six: when you'd pick each side, what it costs you, and what Brew Board chose. Reasonable people land on both sides of most of these, and I'll tell you when that's the case.

1. Whole-view re-render or targeted patches

Part 6 re-renders the whole #app on every change and trusts the morph to keep whatever didn't change. The alternative is to send only the elements a change actually touched. Lesson 8 sends "advance order #3" both ways on a four-row board. The whole board is 316 bytes on the wire; the targeted patch of #order-3 is 114 bytes. But honestly, the bytes are the boring part. The interesting difference is what happens on screen.

The morph keeps identity. patchElements.ts finds an element with a matching id and moves it (moveBefore where the browser has it, insertBefore otherwise) instead of tearing it down and rebuilding it. So listeners and the element's own state survive a re-sort. What does not survive is position on screen. If the server's sort order changes, rows move, and whatever was under the user's pointer a moment ago can be something else now. That's how you get a barista tapping "done" on the wrong latte.

whole viewtargeted patches
renderersone view function; the page GET and the stream share itone per patched region; share them with the page or they drift
derived contentcounts, sorts and headings are always rightstale unless you also patch every region the change touches
server knowledgeonly "something changed"exactly which elements changed
bytesthe whole view; part 6 measured 39–44 bytes per update through a shared deflate streamsmall without compression
content movingyes, when sort order changesno; that's also why the sort goes stale
reconnectsame code path: render the viewneeds a full render anyway

Pick whole view by default, especially for live views with several viewers. It's the one approach where forgetting a region is flat-out impossible, and "forgot to update the count in the header" is a bug you will otherwise write, I promise. Pick targeted patches for a large editable grid where a save shouldn't yank the row out from under the person editing it, or when one region updates way more often than the rest. Even then, the page and the fragment endpoint must call the same render function. Must. Otherwise they drift, and they always drift.

Want to keep whole-view rendering but stop rows from jumping around? A few options:

  • Sort by something that doesn't change while people work, such as order id or arrival time, and show status with a style instead.
  • Put each status in its own section, so an order leaves one list and joins another, which is a move people's eyes can actually follow.
  • Pass useViewTransition (part 2) so the browser animates the move instead of teleporting it.

Brew Board chose: whole view, sorted by status. That's fine for a barista who watches the board, and a known hazard for one who clicks fast. We know. We left it in so you'd see it.

2. text/html or SSE for reads

Remember part 1? Datastar will happily take a plain text/html response and patch its top-level elements by id. No event stream required. Lesson 8 answers the same menu read both ways: 232 bytes of HTML, or 280 bytes as one SSE event. And here's the bit people miss: patch options can travel in response headers (datastar-selector, datastar-mode, …), so even an append works without SSE:

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
datastar-selector: #menu-card
datastar-mode: append

<li>Seasonal: Pumpkin Latte</li>

Pick text/html for reads that return one element. The handler is a plain old Ring handler, you can open the URL in a browser tab and actually look at the fragment, and there's no event framing to get wrong. Pick SSE when one response has to carry several patches, element and signal patches together (part 4's drop-down sends both), or when you need a stream held open over time.

Brew Board chose: SSE everywhere, so the one writer from part 2 covers every case and there's exactly one thing to understand. A production codebase commonly splits it instead: reads are text/html, and writes that need several patches are SSE. Neither is wrong. This is one of those both-sides ones.

3. HTML or signals for values the server sends

The server can get a value onto the screen in two ways. It can render it into HTML, or it can patch-signals it into a signal that a data-text displays. To the user, they look identical. Over time, they behave very differently:

  • HTML gets replaced by the next render. There's nothing to keep in sync, because there's nothing left over.
  • A signal is a client-side copy of server state, and it hangs around until somebody overwrites it. Under a whole-view re-render, an element that displays a signal also ends up wrestling with the morph.

That's why parts 3–7 kept moving prices and error messages into HTML. It wasn't fussiness. It was self-defense.

Use patch-signals when the server is writing into something the client owns. Part 4's drop-down resets $size because the user's draft lives in signals and the old size isn't valid for the new drink. Clearing an input after a successful command is the same case. Use HTML for everything the user only reads, which is to say, most things.

4. Request ordering and cancellation

Here's a fun fact that ruins people's afternoons: two requests in flight can finish in either order. The network makes no promises. Datastar has exactly one built-in rule for this, in fetch.ts. A module-level map holds one AbortController per method and URL, and a new request aborts the one in flight under the same key (default requestCancellation: 'auto'). And now the subtle part, so lean in. The key is the URL string exactly as written in the action, before Datastar appends its datastar parameter. So two @get('/search') calls cancel each other, while @get('/search?q=la') and @get('/search?q=lat') don't. They're different strings, so as far as Datastar's concerned they're strangers.

This isn't just theory. In a real Chrome run against lesson 8's page, typing "lat" quickly into the per-query-URL box left the results showing an earlier, shorter query. The other two boxes showed "lat", as you'd hope. So what do you do about it? Your options:

designproscons
one URL, query in signals: @get('/search')no server code; the browser drops the stale answerthe URL no longer describes the query; aborting is client-side, so the server still runs the old handler
sequence number: $seq = $seq + 1; @get('/search?q=' + …), server answers 204 to an overtaken seqURLs stay meaningful; the server knows a query was supersededa counter signal, plus per-tab state on the server

Note that debounce is in there mostly so I can tell you it doesn't fix this. It's a load fix wearing a correctness costume. You can combine the table's choices, though: debounce for load, plus one of the first two for correctness. And requestCancellation: 'disabled' exists for the rare case where you really do want both answers. Brew Board chose: nothing, technically, because it has no search box, and its commands are different URLs that shouldn't cancel each other anyway. But if you do part 4's searchable-combobox stretch exercise, use one URL.

5. data-indicator or a hand-managed flag

Everybody's first attempt at "disable Save while saving" looks like this: $saving = true; @post('/save'), with the server clearing $saving in its response. It works great right up until the network drops. Then no response arrives, nobody clears the flag, and the page stays locked until reload. Your user stares at a grayed-out button and contemplates the void. data-indicator doesn't have this problem. It counts the element's in-flight fetches, and fetch.ts dispatches the finished event in a finally block, so the count comes down after success, an error status, or a dropped connection. The one catch, which you'll remember from part 3: it only counts fetches started from the element that carries it.

Brew Board chose: data-indicator. We looked for a case where the flag is better. We didn't find one. This is the sacred cow.

6. Per-tab or per-browser identity

Part 6 found this bug the hard way. A cookie identifies a browser, every tab shares it, and so per-cookie state shows up in every tab, whether you wanted it there or not. The split Brew Board eventually settled on:

  • Per browser (the sid cookie): things that belong to the person. That's the cart, the orders, and the registered push device.
  • Per tab (a tabid signal): things that belong to one view. That's the draft being configured and the error message about it.

The tab id is seeded exactly once, with data-signals:tabid__ifmissing="crypto.randomUUID()" on <body>, safely outside every morph target. It's fresh on each full load, stable across re-renders, and (like every non-_ signal) sent along with every request. One small gotcha: crypto.randomUUID() needs a secure context, which means https, or localhost during development.

The code is in clojure/src/lesson08/field_guide.clj (ns lesson08.field-guide), with tests in clojure/test/lesson08/field_guide_test.clj. The demo prints:

  • the read answered as HTML, as SSE, and as an append through headers
  • the whole-view and targeted patches with byte counts and final row order
  • the search race, unguarded and with the sequence-number guard

Run it with cd clojure && clojure -M -m lesson08.field-guide. Or, better, at the REPL, run (lesson08.field-guide/start! 8080) and open http://localhost:8080/, then click through the patches, type into the three search boxes, and open the two receipts. So here's the whole field guide on one napkin. Put each interaction on the highest rung of the ladder that can do it (server, native HTML, CSS, Datastar attributes, custom JS), and make every line of glue justify itself. Navigate with links and full loads, and keep bookmarkable state in the URL. Everything else is a trade-off, not a rule:

  • whole-view rendering trades bytes and moving content for one renderer that can't go stale
  • text/html is enough for one-element reads
  • the server sends HTML for values the user reads, and signals only for what the client owns
  • the URL string you write decides which requests cancel each other
  • data-indicator always comes down after a request
  • per-tab state needs a tab id
