Replacing the React Native app

Brew Board's customer app doesn't need its own UI code. A thin native shell, a WKWebView on iOS and a WebView on Android, loads the same Clojure routes the browser does. The server tells the shell how to navigate, and a small bridge carries native features in and out as events and signals. A new screen ships with a server deploy. Here is how it works, and what it costs.

Picture the app this replaces, because it is the usual one. Brew Board's customers order on their phones through a React Native app. It has its own screens (menu, drink customizer, cart, order status), its own client state (a store holding the cart and the orders), and its own API: a set of JSON endpoints written for the app. The barista board is a web page. So the same orders are rendered twice, by two codebases in two languages, and every change to what a customer sees goes through a build, App Review, and a rollout that some users won't install for weeks. Meanwhile the server has to keep the old JSON shapes working for them.

Parts 1–6 built the web customer page: server-rendered views, signals for input, commands that change an atom, and a live stream that keeps every open view current. Everything that page does, the phone app does too. The question is how little native code it takes to put that page in a store app that still feels like an app.

The shell

The shell is a native app whose screens are web views. It does the things only native code can do, and nothing else:

  • Navigation chrome. A native navigation bar, back gesture and modal sheets. Each screen in the native stack is a web view showing one URL.
  • Native capabilities. Push notification registration, haptics, local notifications, and later the camera or the wallet, each reached through the bridge.
  • Identity. It appends BrewShell/1 to the web view's User-Agent, so the server knows when it's rendering for the shell and which shell version it's talking to.

What the shell does not contain: any Brew Board screen, any drink, any price, any knowledge of orders. Those are all server routes, the ones you already have.

On the server, the first change is one predicate and a layout switch:

(defn shell-request? [req]
  (boolean (some-> (get-in req [:headers "user-agent"])
                   (string/includes? "BrewShell/1"))))

(defn page [{:keys [title shell? signals stream-url]} view]
  (str "<!DOCTYPE html>"
       (h/html
        [:html {:lang "en"}
         [:head [:meta {:charset "utf-8"}]
                [:meta {:name "viewport" :content "width=device-width, initial-scale=1"}]
                [:title title]
                [:script (raw-string bridge-shim)]
                [:script {:type "module" :src datastar-src}]]
         [:body (when signals {:data-signals (json/generate-string signals)
                               :data-signals:tabid__ifmissing "crypto.randomUUID()"})
          (when-not shell?                                   ;; the shell draws its own nav bar
            [:nav.web-nav [:a {:href "/"} "Order"] " · " [:a {:href "/board"} "Board"]])
          [:div {:data-on:brew:native__window "…see below…"}]
          (when stream-url [:div {:data-init (str "@get('" stream-url "', {retry: 'always'})")}])
          view]])))

From lesson07.native-shell. Handlers call it with :shell? (shell-request? req). Note {retry: 'always'} on the stream: part 6's advice for streams that the server may end cleanly, e.g. on a deploy. The tab id is part 6's too; a web view is a tab like any other, with its own draft. (A shell loading https:// is a secure context, so crypto.randomUUID() is there.)

In the shell, the web nav goes (the shell has a native one), and nothing else changes. The #app view, the live stream, the drop-down and the commands are byte-for-byte the same. (A real app would also add viewport-fit=cover and CSS env(safe-area-inset-*) padding to keep content clear of the notch and home indicator. The toy doesn't.)

Navigation is served, not compiled in

When a link in a web view is tapped, the shell intercepts the navigation (on iOS, the WKNavigationDelegate decides each navigation's policy; on Android, WebViewClient.shouldOverrideUrlLoading). It cancels the in-page load and decides how to present the URL: push a new screen onto the stack, show it as a modal, or reset to the root. The rules for that decision come from the server:

GET /native/path-config

{"rules": [
  {"patterns": ["^/$"],            "presentation": "root"},
  {"patterns": ["^/orders/\\d+$"], "presentation": "push"}
]}

The shell fetches this on launch and matches each tapped URL's path against the patterns in order. The first match wins, and a path that matches nothing is pushed. /orders/1 is a real route, GET /orders/:id, a small page showing one of Ada's orders, and when she taps it in her order list the shell pushes it as a new screen with a native back button. Because the rules come from the server, changing them is a server deploy. Present order pages as a sheet instead? Change "push" to "modal" (both reference shells in native/ handle it). Add an order history screen? Render /orders/history, add a pattern, link to it.

Hotwire Native (37signals' iOS and Android libraries for wrapping Turbo apps) uses the same idea, which is where ours comes from. Its path configuration is JSON with rules, each a list of patterns and a properties map. In their demo, "context": "modal" presents forms as modals, "view_controller": "numbers" routes a path to a fully native screen, and "presentation": "clear_all" on ^/$ resets the stacks. It loads the configuration from a bundled file and a remote URL. One difference: Hotwire Native on iOS moves a single WKWebView between view controllers, rather than one web view per screen as in our toy, which saves memory and keeps one JavaScript context alive.

The bridge

A web view runs your page's JavaScript, and both platforms give you a channel between that JavaScript and native code. Brew Board's bridge is a handful of lines on each side.

Web → native. The page defines one function. It forwards a message to whichever native channel exists, and does nothing in a plain browser:

<script>
  window.BrewShell = {
    post(msg) {
      if (window.webkit?.messageHandlers?.brew) window.webkit.messageHandlers.brew.postMessage(msg);  // iOS
      else if (window.BrewAndroid) window.BrewAndroid.postMessage(JSON.stringify(msg));               // Android
    }
  };
</script>

On iOS, brew is a WKScriptMessageHandler the shell registered on the web view's WKUserContentController. On Android, BrewAndroid is an object added with addJavascriptInterface, whose postMessage is annotated @JavascriptInterface. The server triggers it with part 2's execute-script, which appends a self-removing <script> to the body:

(defn bridge-script [msg]
  (sse/execute-script (str "window.BrewShell.post("
                           (string/replace (json/generate-string msg) "</" "<\\/")
                           ")")))

(bridge-script {:type "haptic" :style "success"})
;; event: datastar-patch-elements
;; data: selector body
;; data: mode append
;; data: elements <script data-effect="el.remove()">window.BrewShell.post({"type":"haptic","style":"success"})</script>

The string/replace is not decoration. The message can contain text a user typed (a customer's name), and the HTML parser ends a <script> at the first </script, whatever JSON thinks. A customer named </script> would close the tag early, and whatever follows would be parsed as HTML. <\/ means the same thing in a JavaScript string, but it can't end the tag. The exercise test checks exactly that name.

Native → web. The shell dispatches a DOM event on window (iOS evaluateJavaScript, Android evaluateJavascript):

window.dispatchEvent(new CustomEvent('brew:native', {detail: {type: 'push-token', token: 'a1b2…'}}))

and the page handles it with an ordinary Datastar attribute, on a <div> that every page renders:

<div data-on:brew:native__window="evt.detail.type === 'push-token'
    && ($pushToken = evt.detail.token,
        @post('/native/device', {filterSignals: {include: /^pushToken$/}}))"></div>

One expression: && guards, and the comma operator sequences the assignment and the post. That is the lesson's style. A ;-separated version, or an if block, works just as well in data-on: we ran if (…) { $pushToken = …; $count = $count + 1 } against the v1.0.4 bundle. Datastar splits at ; only for attributes that return a value, such as data-computed, so that it can return the last statement.

We checked that this key works in Datastar's source. The attribute key is split at the first colon (on / brew:native), the __window modifier puts the listener on window, and data-on leaves the event name alone apart from an optional __case modifier, so the listener is for brew:native exactly. evt is the event. Setting $pushToken and posting means the token arrives at POST /native/device as an ordinary signal, read by the same read-signals as everything else, and stored as :devices {sid token} by a :register-device command. The filterSignals option keeps the rest of the page's signals (the draft, the name) out of that request. From the server's side, native features are just more signals and commands.

Only ever load your own origin in the shell. A message handler accepts messages from whatever page is loaded, and an Android addJavascriptInterface object is visible to every page and frame in that web view. Send other URLs to the system browser. On iOS, a handler can also check message.frameInfo.securityOrigin before acting.

The payoff: "Ada, your order #1 is ready."

Part 6 already sends Ada's whole view whenever her order changes. The shell adds one thing: when an order turns :ready, her stream also carries a bridge script. The diff that decides who to notify is a pure function of the old and new state, like everything else:

(defn ready-notifications [old new]
  (for [{:keys [id sid customer status]} (vals (:orders new))
        :when (and (= :ready status) (not= :ready (get-in old [:orders id :status])))]
    {:sid sid :message (str customer ", your order #" id " is ready.")}))

(defn watch! [!state hub]
  (add-watch !state ::live
    (fn [_ _ old new]
      (when (not= old new)
        (broadcast! hub !state)
        (doseq [{:keys [sid message]} (notify! hub (ready-notifications old new))]
          (when-let [token (get-in new [:devices sid])]
            (push! token message)))))))

notify! sends a bridge-script ({:type "notify" … :haptic "success"}) to every open stream of that sid (every tab of that customer: a notification is per customer, unlike the draft), and returns the notifications that found no open stream. Those fall back to push!.

When Sam taps Advance on order #1 for the second time, Ada's phone gets the re-rendered view (status "ready") and a success haptic with a notification banner. It took no new screen, no new API endpoint, and no new app version, provided the installed shell already knows the "notify" message. That condition is the real boundary of this architecture.

One honest limit. A web view's stream only runs while the app is in the foreground. Part 6's rule (a hidden page closes its @get) applies, and iOS suspends backgrounded apps anyway. For "your order is ready" while the phone is in Ada's pocket, the server must send a real push notification (APNs on iOS, FCM on Android) to the token it got through /native/device. That's the fallback in watch!: when notify! finds no open stream for Ada, the toy's push! prints what a real server would send to APNs or FCM for her registered token. It's the one place where the server talks to a platform service instead of a page.

What ships without a release

The rule: anything that is HTML, signals, routes, path rules, or a bridge message the installed shell already understands ships with a deploy. Anything that needs new native code ships with a store release. The /1 in BrewShell/1 is there so the server can tell which messages a given install understands, and send a "scan-qr" message only to shells that can handle it.

Apple's guidelines bear on this in two places, and it is worth reading them rather than relying on folklore. Guideline 4.2 Minimum Functionality says "your app should include features, content, and UI that elevate it beyond a repackaged website," and 4.2.2 says apps shouldn't primarily be "web clippings, content aggregators, or a collection of links." A shell that only loads a URL is the thing 4.2 describes. Native navigation, push notifications, haptics and real native features are what make the difference. Guideline 2.5.2 says apps may not "download, install, or execute code which introduces or changes features or functionality of the app." Web content in a WebKit view is how every hybrid app works (2.5.6 requires WebKit for browsing the web, and 4.7 explicitly allows HTML5 mini apps under conditions). But using server deploys to turn the app into something different from what was reviewed is exactly what 2.5.2 is about. Ship new screens of the same app, not a new app. (Quotes from Apple's App Review Guidelines, checked October 2026. Review is a human judgment, so treat this as risk to manage, not a rule you can rely on.)

What you give up

This is not free, and the trade-offs decide whether it fits.

  • Offline. Every screen is rendered by the server, so no network means no screen. A React Native app can keep its store and show cached orders. For a coffee order, which needs the shop's server anyway, that's fine. For a field app used in basements, it isn't, unless you build the offline screens natively.
  • Latency. Every command is a round trip, and on a phone network that is noticeable. Signals soften it: local feedback (data-indicator, a data-show spinner, a data-class pressed state) happens instantly in the browser, and the server's answer lands a moment later. But a client-side app can be truly optimistic in ways this architecture discourages.
  • Gestures and animation. Swipe-to-dismiss cards, drag-to-reorder, physics-driven transitions tied to the finger: these belong in native code or React Native, and a web view gives you CSS transitions and view transitions instead. Native navigation transitions come back because the shell does them, but in-screen interaction is web-grade.
  • Platform conventions. A web view renders your CSS, not UIKit or Material components. Users notice date pickers, lists, and text fields that behave slightly differently. Native controls where it matters (a native date picker via the bridge, say) cost native code and a release.
  • Background work. No live stream in the background. Anything that must happen while the app is closed (push, location, sync) is native.

When to keep React Native (or go fully native): offline-first apps, apps whose core is rich touch interaction (maps, editors, media), apps with heavy on-device computation, and teams whose real product is the mobile client with the server as a data API. Brew Board is none of those. It's a set of forms and lists over shared, live server state, which is the shape where sending HTML wins most clearly.

Hyperview (from Instawork) keeps the server-driven model but drops the web view. The server sends Hyperview XML (HXML), a hypermedia format designed around mobile UI patterns, and a React Native client renders it with native components. Its pitch is the same as ours ("update your apps instantly by deploying your backend"), traded for a new markup language instead of HTML. It's worth a look when native controls matter more than reusing the web page.

What the series built

Look back at what the native app needed from the server: a predicate on the User-Agent, a JSON file of path rules, one route for the push token, and a pure function deciding who to notify. Every screen it shows came from parts 1–6: hand-written SSE events (part 2), signals for what the user is doing (part 3), the server owning everything shared (part 4), a small route table of queries and commands (part 5), and one stream per page that re-renders the whole view and morphs it in (part 6). The mobile app is the web app, plus a shell.

A native shell is a stack of web views showing your server's routes, plus navigation rules it downloads, plus a bridge: native → web as DOM events that become signals, web → native as scripts the server sends. Screens, layouts, and anything the installed shell already understands ship with a deploy. New native capabilities ship with a release, and the shell version in the User-Agent tells the server which is which. You give up offline use, finger-driven interaction, and some platform polish, so it fits apps made of forms and lists over live server state.
