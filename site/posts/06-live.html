One stream, many viewers

Every open page holds one long-lived GET. Commands change the atom and answer 204. When the atom changes, the server renders each viewer's whole view again and sends it down that viewer's stream; Datastar's morph applies only the difference. It sounds wasteful. Measured, it costs about 40 bytes per update, and it never loses the user's focus.

Part 5 ended with Sam's board stale. Ada placed an order, her own page updated, and the board, open in another browser, never heard about it. A response can only go to the browser that asked, and Sam's browser didn't ask.

The fix is to have every page ask once, at load, and keep asking: one GET whose response never ends. While it is open, the server can write to it whenever it likes. That turns the server from "answer requests" into "keep every open view current", and once it can do that, commands don't need to return any HTML at all.

The shape

-- on page load
browser: data-init="@get('/customer/stream')"      -- request stays open
server:  subscribe(sid, send)                       -- remember how to reach this page
server:  send(render(view-for(sid, state)))        -- the whole #app, right now

-- on any command
browser: @post('/orders')                           -- same request as part 5
server:  swap!(state, handle-command, cmd)          -- same pure function as part 5
server:  respond 204                                -- nothing else
-- the atom's watch runs next
for each subscriber s
  html = render(view-for(s, new-state))
  if html != s.last-sent then send(s, patch-elements(html))

Two things moved compared with part 5. The response to a command is now empty: Datastar accepts a 204 and does nothing with it (no patch, no retry). And the decision "what changed on which page" has disappeared. There is no command-response. There is one function per kind of page, view-for, that renders the whole page body from the state, and one rule: after every change, render every view again.

Holding a stream open in http-kit

Parts 1–5 returned one-shot responses: an ordinary Ring map whose body was the concatenated events. Datastar read to EOF and stopped. A held-open stream needs a body that doesn't end, which in http-kit means as-channel:

(defn stream-handler [hub !state viewer]
  (fn [req]
    (let [{:keys [on-open on-close]} (stream-lifecycle hub !state viewer)]
      (hk/as-channel req
        {:on-open  (fn [ch]
                     (hk/send! ch {:status  200
                                   :headers {"Content-Type"  "text/event-stream"
                                             "Cache-Control" "no-cache"
                                             "Connection"    "keep-alive"}}
                               false)                     ;; false: keep the channel open
                     (on-open #(hk/send! ch % false)))    ;; send-fn: one string in
         :on-close (fn [_ch _status] (on-close))}))))

(defn stream-lifecycle [hub !state viewer]
  (let [id (random-uuid)]
    {:on-open  (fn [send-fn]
                 (subscribe! hub id send-fn viewer)     ;; :last starts nil…
                 (broadcast! hub @!state))              ;; …so this sends the whole view now
     :on-close (fn [] (unsubscribe! hub id))}))

viewer is {:kind :customer :sid sid} or {:kind :board}. stream-lifecycle knows nothing about http-kit, so the tests drive it with a send-fn that conj's onto an atom.

send! with close? false writes and keeps the connection. The first send! carries the status and headers. http-kit is non-blocking, so an idle stream holds a socket and a small amount of memory, not a thread. Check that your server really tells you when a viewer leaves: on http-kit 2.8.1, :on-close never fired when an SSE client disconnected and send! kept returning true, so the hub went on rendering for closed tabs. The course pins 2.9.0-beta4, where it fires. on-open immediately sends the subscriber its whole view, so the page is correct the moment the stream opens, whatever happened before.

The hub is an atom of subscribers plus a watch on the state atom:

(defn broadcast! [hub state]
  (locking hub
    (into []
          (keep (fn [[id {:keys [send-fn viewer last]}]]
                  (let [view (html (view-for state viewer))]
                    (when (not= view last)
                      (send-fn (sse/patch-elements view))
                      (swap! hub assoc-in [id :last] view)
                      id))))
          @hub)))

(add-watch !state ::broadcast (fn [_ _ old new] (when (not= old new) (broadcast! hub new))))

From lesson06.live. locking keeps two broadcasts from interleaving their sends and :last updates. It returns the ids it sent to, which is what the tests check.

The :last check matters more than it looks. Most changes touch one person's view. When Grace adds a mocha to her cart, Ada's page renders to exactly the same string, so nothing is sent to Ada. The drink choice has to move to the server

That passage skipped a question. To render Ada's #drink-options, the server needs to know which drink she picked: a latte has three sizes and three milks, an espresso has single/double and no milk. In part 4 the drink lived only in the $drink signal, and GET /drink-options read it from the request. A whole-view render triggered by Sam's command has no request from Ada to read it from. Her stream is a GET that was opened once, at page load, so the signals it carried describe the page as it was then. They are never updated, because Datastar sends signals with requests and the stream makes no new ones (it rebuilds them only on reconnect).

The rule this teaches: state that shapes server-rendered HTML must live on the server. So in lessons 06–07 and the capstone, changing the drink becomes a command. The select runs @post('/draft'), and :choose-draft stores :drafts {sid {:drink :size :milk}} in the atom. The command answers 200 with a patch-signals of whichever of size/milk became invalid for the new drink, or 204 if neither did. The new option lists arrive the usual way, in the whole-view re-render that the swap! triggers. Part 4's GET /drink-options stays what it was there: a pure query, for pages without a live stream.

One more detail makes this safe to re-render. In lessons 06–07, drink-options-view takes [drink sold-out] and renders no selected attribute; which option is chosen is the bound signal's business. That matters because of how the morph treats options. In patchElements.ts, morphNode sets an option's selected property only when the presence of the selected attribute differs between the old and new option. With no selected attribute on either side, a re-render never touches the selection that data-bind:size made, so Ada's medium stays medium while Sam's changes stream in.

"Sending the whole view on every change is too much"

There are two objections. Each one is reasonable, and neither holds up.

Bytes. A Brew Board barista view with 12 orders is 2,613 bytes as an SSE event. Advance one order and the next render is another 2,613 bytes, almost all of them identical to the last. Gzip each event on its own and you get about 540 bytes. But a long-lived stream can share one compression context across events: run the stream through one deflate stream, flushing after each event. Then each re-render can refer back to the previous one. We ran that over twelve successive renders, each advancing one order: the first event is 526 bytes, and every later one is 39 to 44 bytes. Plain http-kit does not compress for you. Datastar's Clojure SDK ships gzip and Brotli "write profiles" for this reason, and you can wrap the output stream yourself the same way. (Deflate looks back at most 32 KB, so a view much bigger than that compresses less well against its predecessor. Brotli allows larger windows.)

CPU. Each change renders one view per subscriber, so the cost is subscribers × changes × render time. For a coffee shop that is nothing. For thousands of viewers of a fast-changing view, you'd render once per distinct view instead of once per subscriber (all baristas see the same board), and throttle (render at most every 100 ms, sending the latest). Both are changes inside broadcast!. No handler and no view changes.

Focus and typing are the objection people actually worry about, and they need the morph. Predict first.

How the morph keeps your place

A datastar-patch-elements event with no selector and the default mode outer finds the element with the same id as each top-level element sent (<main id="app"> here) and morphs it into the new HTML. Morphing doesn't replace the old element. It walks the old and new trees together and changes the existing DOM nodes until they match. A node that survives is the same object it was before, so everything the browser keeps on that object survives with it: focus, cursor position, the text typed into an input, scroll position, running CSS transitions.

Here is the algorithm in library/src/plugins/watchers/patchElements.ts, reduced to its decisions:

function morph(old, new)
  persistent = ids present in both trees on the same tag, minus duplicates
  idSets     = for every element: the persistent ids somewhere inside it
  morphChildren(old.parent, [new])

function morphChildren(oldParent, newParent)
  cursor = first old child
  for each newChild in newParent.children
    match = findBestMatch(newChild, from cursor)
      -- 1st choice: same tag, and their id sets share an id (hard match)
      -- 2nd choice: same tag, and the old one has no id or the same id (soft match)
    case match of
      found      -> remove old nodes between cursor and match; morphNode(match, newChild)
      elsewhere  -> if newChild.id is persistent: move that old node here, morphNode it
      none       -> insert a copy of newChild              -- new DOM, no old state
    cursor = next after it
  remove old children left after the cursor

function morphNode(old, new)
  if input: set old.value only if the value ATTRIBUTE differs   -- typing survives
  copy attributes new -> old; remove attributes new lacks
  if not old.isEqualNode(new) then morphChildren(old, new)       -- equal subtrees skipped
  if text node: copy nodeValue if different

Two details there decide whether your view is morph-friendly.

Inputs keep what the user typed because morphNode compares the value attribute of old and new, not the live value. Brew Board renders <input id="customer" data-bind:customer> with no value attribute, so the comparison is null vs null, nothing is set, and "Ad" stays in the box with the cursor after the d. If you render value="…" from server state, a change to that value will overwrite what the user is typing. Datastar also gives you data-preserve-attr to leave named attributes alone and data-ignore-morph to leave an element untouched (it applies when both the old and the new element carry it).

Ids are how the morph keeps identity across moves. A matched element with a persistent id can be moved to its new position instead of being rebuilt. When Sam advances order #1, its <li id="board-order-1"> moves from the "placed" column to "making" as the same node. Give an id to anything that holds state (inputs, selects, expanded panels) and anything that moves (list items). Ids must be unique: the morph drops duplicated ids from the persistent set.

Switch the figure to replace mode to see the alternative. replace swaps the element for a fresh copy (replaceWith): correct HTML, but every node is new, so the input is empty and the focus has gone to <body>. That is what an innerHTML re-render does in a hand-written app, and it's why people believe "send the whole page" can't work. With a morph it does.

Reconnects

A stream that is open for an hour will break: Wi-Fi drops, a laptop sleeps, a deploy restarts the server. What Datastar does about it is in fetch.ts:

  • If the connection fails or the stream errors, Datastar retries with backoff: first after retryInterval = 1,000 ms, then ×retryScaler = 2 each time, capped at retryMaxWait = 30,000 ms, up to retryMaxCount = 10 tries (1, 2, 4, 8, 16, 30, 30, 30, 30, 30 s: about 3 minutes in total). A successful connection resets the count. A server retry: line in the stream overrides the interval.
  • If the server ends the stream cleanly, the default retry: 'auto' does not reconnect. Only retry: 'always' does. So don't close live streams on purpose, and check what your server does on a graceful shutdown: if it ends each stream properly, pages won't come back after a deploy. Opening the stream with @get('/customer/stream', {retry: 'always'}) covers that case.
  • A @get closes when the tab is hidden and reopens when it becomes visible again (openWhenHidden defaults to false for GET and to true for the other methods). A phone that locks drops its stream; unlocking opens a new one.
  • Each retry rebuilds the request, so it carries the signals as they are now, and the last-event-id header if the server sent event ids.

Because on-open sends the whole current view, a reconnect needs no catching up. There is no "missed events" problem to solve with event ids and a replay buffer. The new connection gets the truth, and the morph lands it on whatever the page was showing.

One stream per page, opened from data-init on an element that stays put (the <body> or a wrapper outside #app). Datastar's default requestCancellation: 'auto' aborts an in-flight request when the same method and URL is requested again from that page, so a second @get('/customer/stream') replaces the first rather than doubling up.

What the server keeps and what it doesn't

The hub holds, per open page: the channel's send function, what kind of view it is (:customer sid or :board), and the last HTML sent. It does not hold any per-page UI state. Which drink is selected, what is typed, whether a panel is open: those are signals and DOM, and they stay in the browser, protected by the morph. The server owns what is shared (orders, stock, carts). The browser owns what is personal and short-lived. That is part 4's split, enforced by the architecture this time rather than by discipline.
