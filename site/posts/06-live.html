One stream, many viewers

Every open page holds one long-lived GET. Commands change the atom and answer 204. When the atom changes, the server renders each viewer's whole view again and sends it down that viewer's stream; Datastar's morph applies only the difference. It sounds wasteful. Measured, it costs about 40 bytes per update, and it never loses the user's focus.

Part 5 ended with Sam's board stale. Ada placed an order, her own page updated, and the board, open in another browser, never heard about it. A response can only go to the browser that asked, and Sam's browser didn't ask.

The fix is to have every page ask once, at load, and keep asking: one GET whose response never ends. While it is open, the server can write to it whenever it likes. That turns the server from "answer requests" into "keep every open view current", and once it can do that, commands don't need to return any HTML at all.

The shape

-- on page load
browser: data-init="@get('/customer/stream')"      -- request stays open
server:  subscribe(viewer, send)                    -- viewer: sid cookie + tab id
server:  send(render(view-for(viewer, state)))     -- the whole #app, right now

-- on any command
browser: @post('/orders')                           -- same request as part 5
server:  swap!(state, handle-command, cmd)          -- same pure function as part 5
server:  respond 204                                -- nothing else
-- the atom's watch runs next
for each subscriber s
  html = render(view-for(s, new-state))
  if html != s.last-sent then send(s, patch-elements(html))

Two things moved compared with part 5. The response to a command is now empty: Datastar accepts a 204 and does nothing with it (no patch, no retry). And the decision "what changed on which page" has disappeared. There is no command-response. There is one function per kind of page, view-for, that renders the whole page body from the state, and one rule: after every change, render every view again.

Tip. The page GET and the stream must call the same view function. In the lesson, GET / embeds (view-for state viewer) and the stream sends (view-for state viewer); there is no second renderer for "the first paint". Two renderers drift, and the first stream event would then visibly rewrite the page the user just loaded.

Holding a stream open in http-kit

Parts 1–5 returned one-shot responses: an ordinary Ring map whose body was the concatenated events. Datastar read to EOF and stopped. A held-open stream needs a body that doesn't end, which in http-kit means as-channel:

(defn stream-handler [hub !state viewer]
  (fn [req]
    (let [{:keys [on-open on-close]} (stream-lifecycle hub !state viewer)]
      (hk/as-channel req
        {:on-open  (fn [ch]
                     (hk/send! ch {:status  200
                                   :headers {"Content-Type"  "text/event-stream"
                                             "Cache-Control" "no-cache"
                                             "Connection"    "keep-alive"}}
                               false)                     ;; false: keep the channel open
                     (on-open #(hk/send! ch % false)))    ;; send-fn: one string in
         :on-close (fn [_ch _status] (on-close))}))))

(defn stream-lifecycle [hub !state {:keys [sid tabid draft] :as viewer}]
  (let [id (random-uuid)]
    {:on-open  (fn [send-fn]
                 (when tabid                            ;; a customer tab: adopt its draft
                   (swap! !state handle-command {:type :open-tab :sid sid :tabid tabid
                                                 :stream id :draft draft}))
                 (subscribe! hub id send-fn (dissoc viewer :draft)) ;; :last starts nil…
                 (broadcast! hub @!state))              ;; …so this sends the whole view now
     :on-close (fn []
                 (unsubscribe! hub id)
                 (when tabid
                   (swap! !state handle-command {:type :close-tab :tabid tabid :stream id})))}))

viewer is {:kind :customer :sid … :tabid …} (plus the :draft the stream's request carried) or {:kind :board}. The tab parts are explained below, in "A cookie identifies a browser, not a tab". stream-lifecycle knows nothing about http-kit, so the tests drive it with a send-fn that conj's onto an atom.

send! with close? false writes and keeps the connection. The first send! carries the status and headers. http-kit is non-blocking, so an idle stream holds a socket and a small amount of memory, not a thread. Check that your server really tells you when a viewer leaves: on http-kit 2.8.1, :on-close never fired when an SSE client disconnected and send! kept returning true, so the hub went on rendering for closed tabs. The course pins 2.9.0-beta4, where it fires. on-open immediately sends the subscriber its whole view, so the page is correct the moment the stream opens, whatever happened before.

The hub is an atom of subscribers plus a watch on the state atom:

(defn broadcast! [hub state]
  (locking hub
    (into []
          (keep (fn [[id {:keys [send-fn viewer last]}]]
                  (let [view (html (view-for state viewer))]
                    (when (not= view last)
                      (send-fn (sse/patch-elements view))
                      (swap! hub assoc-in [id :last] view)
                      id))))
          @hub)))

(add-watch !state ::broadcast (fn [_ _ old new] (when (not= old new) (broadcast! hub new))))

From lesson06.live. locking keeps two broadcasts from interleaving their sends and :last updates. It returns the ids it sent to, which is what the tests check.

The :last check matters more than it looks. Most changes touch one person's view. When Grace adds a mocha to her cart, Ada's page renders to exactly the same string, so nothing is sent to Ada. The figure shows who gets an event for three different commands. The exercise track has you write view-for, broadcast!, and the on-open/on-close pair (stream-lifecycle).

The third command in the figure is the one part 4 promised. When Sam marks oat milk sold out, every customer's #drink-options renders with <option value="oat" disabled>Oat (sold out)</option>, so every open customer page gets it. No code for that was written in this part. The drop-down is part of the customer's view, the view is rendered from state, and sold-out is state. (The command still checks: add-to-cart rejects a sold-out milk even if a page that hasn't updated yet sends one.)

The drink choice has to move to the server

That passage skipped a question. To render Ada's #drink-options, the server needs to know which drink she picked: a latte has three sizes and three milks, an espresso has single/double and no milk. In part 4 the drink lived only in the $drink signal, and GET /drink-options read it from the request. A whole-view render triggered by Sam's command has no request from Ada to read it from. Her stream is a GET that was opened once, at page load, so the signals it carried describe the page as it was then. They are never updated, because Datastar sends signals with requests and the stream makes no new ones (it rebuilds them only on reconnect).

The rule this teaches: state that shapes server-rendered HTML must live on the server. So in lessons 06–07 and the capstone, the draft becomes a command. All three selects (#drink, #size, #milk) run @post('/draft') on change. :choose-draft fits the draft to the drink (an invalid size or milk becomes the drink's first valid one) and stores it as the tab's draft, [:tabs tabid :draft] (why per tab and not per customer is the next section). The command answers 200 with a patch-signals of whichever of size/milk the fitting changed, or 204 if neither changed. The new option lists arrive the usual way, in the whole-view re-render that the swap! triggers. Part 4's GET /drink-options stays what it was there: a pure query, for pages without a live stream.

Why do the size and milk selects post too, when only the drink changes the option lists? Because the server must also render which option is chosen. Predict this one.

Here is the mechanism, in patchElements.ts. The options have no ids, so findBestMatch pairs them by soft match (same tag, no id), which means in order: old option 1 becomes new option 1, and so on. morphNode then copies the new value attribute and text onto each old option. For options it sets the selected property only when the presence of the selected attribute differs between old and new. Latte's list was small, medium, large with medium chosen at position 2. Chai's list is medium, large. Position 1 becomes "Medium", position 2 becomes "Large" and keeps its selected property, and position 3 is removed. The select shows Large. $size is still medium, which is valid for chai, so the command patches no signal, and data-bind has no change to react to. The screen and the signal now disagree. (A bound element does re-sync when the morph does flip a property: morphNode then fires a datastar-prop-change event, and data-bind listens for it. Here nothing flipped, so nothing fired.)

The general rule: in a whole-view render, render the true current value of every form control you re-render. The morph keeps the browser's state only where old and new markup agree; where the list itself changes, positions get new meanings. So drink-options-view takes [drink sold-out {:keys [size milk]}], the same shape as in part 4, and puts selected on the stored choice. With chai rendered as medium selected, large not, both options' attribute presence changes and the morph sets both properties. And because the stored choice is what gets rendered, it must be real: that's why #size and #milk also @post('/draft'). Otherwise the next re-render would render the old size as selected and undo what Ada picked. Text inputs are the exception that proves the rule: the morph leaves an input's .value alone while its value attribute is unchanged, so #customer, rendered with no value, keeps what Ada types (more on that below).

Tip. This isn't special to <select>. The morph sets an input's .checked and an option's .selected only when that attribute's presence differs between the old and new markup, and .value only when the value attribute differs; a click changes the property, not the attribute. A production app paging a grid this way kept the previous page's ticks in the same positions. Fix it by rendering the true state from the server after every change (what Brew Board does), or by giving the element an id that encodes identity and state (cx-sel-42-1), so the morph replaces it instead of patching it.

A cookie identifies a browser, not a tab

Where should the draft be stored? The obvious key is the sid cookie: it's already on every request, and the cart and the orders use it. That is right for the cart. Ada's cart is Ada's, whichever tab she looks at it from. It is wrong for the draft, because every tab of a browser sends the same cookie, and the draft belongs to the tab whose drop-downs show it.

So per-tab state needs a tab id, and the browser is the only party that knows where one tab ends and another begins. The page seeds one on <body>:

[:body {:data-signals (json/generate-string draft-signals)
        :data-signals:tabid__ifmissing "crypto.randomUUID()"}
 [:div {:data-init "@get('/customer/stream', {retry: 'always'})"}]
 view]

From lesson06.live/page. tabid has no _, so it rides on every request: the stream's GET and every command.

Three details make this work. Datastar applies the root element first and then its descendants in document order (engine.ts), so $tabid exists before the child's data-init opens the stream; keep data-init off <body> itself, because hiccup sorts attributes and data-init would come first. A page load starts with an empty signal store, so every load (a reload, a duplicated tab) gets a fresh id; __ifmissing keeps it stable if the attribute is ever applied again. And crypto.randomUUID() exists only in a secure context: https, or localhost in development. On a plain-http LAN address it is undefined.

The state splits accordingly. :carts, :orders and (in part 7) :devices stay keyed by sid. Per-tab state lives in :tabs {tabid {:sid … :stream … :draft … :error …}}, and each customer subscriber's viewer carries both keys, so view-for renders the browser's cart with the tab's draft.

One more problem: when does the server learn a tab's draft? Not only from /draft. A hidden tab closes its stream and opens a new one when it becomes visible (see Reconnects, below), and a server restart forgets everything. The stream's GET carries the tab's signals as they are at that moment, so opening the stream adopts the draft: the :open-tab command in stream-lifecycle fits the draft from the request and stores it before the first render. The browser and the server agree again on every connect, and :on-close can drop the tab without losing anything. :close-tab checks the stream id, because a reconnect can open the new stream before the old one's close arrives. We checked it in Chrome: hide Ada's tab, which closes the stream; show it again, and the new stream's request carries mocha/large; the re-rendered view matches.

Errors are server state too

A command that fails (adding a sold-out milk, placing an order with an empty cart) still answers 204. It records the message for that tab, [:tabs tabid :error], and the whole-view render draws it like everything else: (when error [:p.error error]). The tab's next command clears it. The alternative is an $_error signal patched by the command and displayed with data-text, but then the server renders that element empty on every re-render and fights the client over its content. The rule from the drop-down applies again: if the server renders it, the server must know it. (Datastar's data-ignore-morph makes the morph skip an element entirely; keep it for widgets the client really owns, such as a third-party editor.)

"Sending the whole view on every change is too much"

There are two objections. Each one is reasonable, and neither holds up.

Bytes. A Brew Board barista view with 12 orders is 2,613 bytes as an SSE event. Advance one order and the next render is another 2,613 bytes, almost all of them identical to the last. Gzip each event on its own and you get about 540 bytes. But a long-lived stream can share one compression context across events: run the stream through one deflate stream, flushing after each event. Then each re-render can refer back to the previous one. We ran that over twelve successive renders, each advancing one order: the first event is 526 bytes, and every later one is 39 to 44 bytes. Plain http-kit does not compress for you. Datastar's Clojure SDK ships gzip and Brotli "write profiles" for this reason, and you can wrap the output stream yourself the same way. (Deflate looks back at most 32 KB, so a view much bigger than that compresses less well against its predecessor. Brotli allows larger windows.)

CPU. Each change renders one view per subscriber, so the cost is subscribers × changes × render time. For a coffee shop that is nothing. For thousands of viewers of a fast-changing view, you'd render once per distinct view instead of once per subscriber (all baristas see the same board), and throttle (render at most every 100 ms, sending the latest). Both are changes inside broadcast!. No handler and no view changes. (Part 8 compares the whole view with the alternative of patching only the elements that changed.)

Focus and typing are the objection people actually worry about, and they need the morph. Predict first.

How the morph keeps your place

A datastar-patch-elements event with no selector and the default mode outer finds the element with the same id as each top-level element sent (<main id="app"> here) and morphs it into the new HTML. Morphing doesn't replace the old element. It walks the old and new trees together and changes the existing DOM nodes until they match. A node that survives is the same object it was before, so everything the browser keeps on that object survives with it: focus, cursor position, the text typed into an input, scroll position, running CSS transitions.

Here is the algorithm in library/src/plugins/watchers/patchElements.ts, reduced to its decisions:

function morph(old, new)
  persistent = ids present in both trees on the same tag, minus duplicates
  idSets     = for every element: the persistent ids somewhere inside it
  morphChildren(old.parent, [new])

function morphChildren(oldParent, newParent)
  cursor = first old child
  for each newChild in newParent.children
    match = findBestMatch(newChild, from cursor)
      -- 1st choice: same tag, and their id sets share an id (hard match)
      -- 2nd choice: same tag, and the old one has no id or the same id (soft match)
    case match of
      found      -> remove old nodes between cursor and match; morphNode(match, newChild)
      elsewhere  -> if newChild.id is persistent: move that old node here, morphNode it
      none       -> insert a copy of newChild              -- new DOM, no old state
    cursor = next after it
  remove old children left after the cursor

function morphNode(old, new)
  if input: set old.value only if the value ATTRIBUTE differs   -- typing survives
  copy attributes new -> old; remove attributes new lacks
  if not old.isEqualNode(new) then morphChildren(old, new)       -- equal subtrees skipped
  if text node: copy nodeValue if different

Two details there decide whether your view is morph-friendly.

Inputs keep what the user typed because morphNode compares the value attribute of old and new, not the live value. Brew Board renders <input id="customer" data-bind:customer> with no value attribute, so the comparison is null vs null, nothing is set, and "Ad" stays in the box with the cursor after the d. If you render value="…" from server state, a change to that value will overwrite what the user is typing. Datastar also gives you data-preserve-attr to leave named attributes alone, and data-ignore-morph: in patchElements.ts, when both the old element and the new one carry data-ignore-morph, morphNode returns the old element as it is, with no attributes copied and no children walked.

Tip. autofocus doesn't help after a morph. Browsers apply it while the page loads; an element the morph patches in place is never "inserted", and one a patch adds later can't count on it. If a re-render should put the cursor somewhere (an editor that a click opened), put data-init="el.focus()" on that element: Datastar runs data-init when the element is added to the page.

Ids are how the morph keeps identity across moves. A matched element with a persistent id can be moved to its new position instead of being rebuilt. When Sam advances order #1, its <li id="board-order-1"> moves from the "placed" column to "making" as the same node. Give an id to anything that holds state (inputs, selects, expanded panels) and anything that moves (list items). Ids must be unique: the morph drops duplicated ids from the persistent set.

Switch the figure to replace mode to see the alternative. replace swaps the element for a fresh copy (replaceWith): correct HTML, but every node is new, so the input is empty and the focus has gone to <body>. That is what an innerHTML re-render does in a hand-written app, and it's why people believe "send the whole page" can't work. With a morph it does.

Reconnects

A stream that is open for an hour will break: Wi-Fi drops, a laptop sleeps, a deploy restarts the server. What Datastar does about it is in fetch.ts:

  • If the connection fails or the stream errors, Datastar retries with backoff: first after retryInterval = 1,000 ms, then ×retryScaler = 2 each time, capped at retryMaxWait = 30,000 ms, up to retryMaxCount = 10 tries (1, 2, 4, 8, 16, 30, 30, 30, 30, 30 s: about 3 minutes in total). A successful connection resets the count. A server retry: line in the stream overrides the interval.
  • If the server ends the stream cleanly, the default retry: 'auto' does not reconnect. Only retry: 'always' does. So don't close live streams on purpose, and check what your server does on a graceful shutdown: if it ends each stream properly, pages won't come back after a deploy. Opening the stream with @get('/customer/stream', {retry: 'always'}) covers that case.
  • A @get closes when the tab is hidden and reopens when it becomes visible again (openWhenHidden defaults to false for GET and to true for the other methods). A phone that locks drops its stream; unlocking opens a new one.
  • Each retry rebuilds the request, so it carries the signals as they are now, and the last-event-id header if the server sent event ids.

Because on-open sends the whole current view, a reconnect needs no catching up. There is no "missed events" problem to solve with event ids and a replay buffer. The new connection gets the truth, and the morph lands it on whatever the page was showing.

One stream per page, opened from data-init on an element that stays put (a child of <body> outside #app). Datastar's default requestCancellation: 'auto' aborts an in-flight request when the same method and URL is requested again from that page, so a second @get('/customer/stream') replaces the first rather than doubling up.

What the server keeps and what it doesn't

The hub holds, per open page: the channel's send function, the viewer (a customer's sid and tabid, or :board), and the last HTML sent. The state atom holds what is shared (orders, stock), what is per customer (carts), and, new in this part, what is per tab but shapes the rendered view (the draft, the error). What the server never renders stays in the browser: what is typed into #customer, the quantity, focus, scroll. Those are signals and DOM, protected by the morph. Part 4's split still holds, with one refinement the live view forces: state that shapes server-rendered HTML moves to the server, keyed as narrowly as it lives.

Tip. Never render data-signals for signals the user owns inside a morph target. When a re-render changes that attribute, Datastar applies it again (its MutationObserver re-runs any changed data-* attribute) and resets what the user typed. That is why the page declares its signals on <body>, outside #app. If a seed must live inside, write it with __ifmissing so it only fills a signal that doesn't exist yet.
