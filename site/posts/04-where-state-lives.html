When to use a signal

Every piece of state in a Datastar app has one home: the server, a signal, a private _ signal, or HTML the server renders. This part gives a rule for choosing, places every piece of Brew Board's state with it, and builds the case where the choice is least obvious: a drop-down whose options depend on the menu and on what's in stock.

Part 3 ended with a smell. The server computed a price and sent it back as a number, so the page had to know where to put it, how to format it, and what to show next to it. Nothing broke. But follow that road for a few weeks and you end up with the whole app's state in signals, every view built from data-text and data-show, and the server reduced to a JSON API. That's a single-page app with fewer tools.

Datastar's design pushes the other way. The server renders HTML, the browser patches it in, and signals carry the little bit of state that only exists in the browser. The hard part is knowing which bit that is.

The rule

Ask these in order. The first "yes" decides.

  1. Does anyone besides this tab need it, or must it survive a reload? Another device, another person, the next page load, the server's own rules. Then it lives on the server. Carts, orders, stock, the signed-in user.
  2. Is it a list or a block of markup that depends on server data? Then the server renders it as HTML. It is never mirrored into a signal. The options in a drop-down, the rows of a table, a "sold out" label.
  3. Is it input the user hasn't committed yet? Then it's a signal. It goes to the server with the request that commits it, and the server validates it. A form in progress, a search box, a quantity stepper.
  4. Is it purely about presentation in this tab? Then it's a _-prefixed signal, which never leaves the browser. Whether a menu is open, which tab is selected, whether a request is in flight.

Values derived from those for display, like part 3's $estimate, can be data-computed for instant feedback, as long as the server computes the real value again whenever it matters. A computed signal is a convenience, never evidence.

Why the cart is not a signal

The cart is the most tempting thing to put in a signal. It's per-customer, it changes on every click, and a $cart array with data-text totals would update instantly. Here is what it would cost:

  • It travels with every request. A non-_ signal is in every payload. Each drop-down change would send the whole cart to /drink-options, which has no use for it.
  • It's a second copy. Ada adds a latte on her phone; her laptop's $cart doesn't know. Reload and the cart is gone, unless you add storage, and then you have three copies.
  • The server has to check it anyway. When the order is placed, the server can't trust the lines or the prices it receives, so it validates everything again. The client copy saved no work.

So the cart lives in the server's state atom, keyed by a session id. The first page load sets a cookie, and Datastar's fetches are same-origin, so every request carries it:

(defn page-response [req]
  (let [sid (or (sid-of req) (str (UUID/randomUUID)))]
    (cond-> (sse/html-response (page @state sid))
      (not (sid-of req)) (assoc :cookies {"sid" {:value sid :path "/" :http-only true :same-site :lax}}))))

(defn add-to-cart
  "Add the draft to the cart of session sid. Return the new state, or nil when the draft is
  not valid (sold-out milks count)."
  [state sid draft]
  (when-not (draft-error draft (:sold-out state))
    (update-in state [:carts sid] (fnil conj []) (select-keys draft [:drink :size :milk :qty]))))

"Add to cart" is @post('/cart/items'). The draft signals arrive as the JSON body. The handler validates them against the menu and the current stock, updates the atom, and answers with two events: the re-rendered #cart as HTML, and {"error": ""} to clear any old message. On a bad draft it sends only {"error": "Oat milk is sold out."}. The cart's markup, its line format, and its total are server code. The browser holds none of it.

Notice what's in the signals and what isn't. The draft (one line being configured) is a signal, because it is input. Once committed, the line becomes server state, and from then on the browser only ever sees it as HTML.

The drop-down

Now the hard case. When the customer picks a drink, the size and milk drop-downs have to change: an espresso comes in single or double and takes no milk, a cappuccino comes in small or medium with whole or oat. And when Sam marks oat milk sold out, oat must show as unavailable.

The SPA reflex is to ship the menu and the stock to the browser as signals and build the <option>s with expressions. Run the rule instead. The option list depends on server data (rule 2), so it's HTML from the server. The selected values are input (rule 3), so they're signals. The drop-down is both, and the boundary runs between the <option> list and the value.

[:select#drink {:data-bind:drink "" :data-on:change "@get('/drink-options')"}
 (for [[k {:keys [name]}] menu]
   [:option (cond-> {:value (clojure.core/name k)} (= k :latte) (assoc :selected "")) name])]
(drink-options-view :latte sold-out choice)

The drink select is bound to $drink and, on change, asks the server for new options. Both data-bind and data-on:change listen to the same change event, so their order matters: the binding has to update $drink before the request serializes the signals. Listeners run in the order they were added, attributes are applied in source order, and hiccup sorts data-bind:drink before data-on:change. The request carries the new drink. (If you ever need to be explicit, read the value from the event instead: evt.target.value.)

The options themselves are a pure function of the drink, the sold-out set, and the current choice:

(defn drink-options-view
  "The #drink-options element: a size select and a milk select for this drink. The option
  lists exist only here, as HTML from the server."
  [drink sold-out {:keys [size milk]}]
  (let [{:keys [sizes milks]} (menu drink)]
    [:div#drink-options
     [:label "Size "
      [:select#size {:data-bind:size ""}
       (for [s sizes]
         [:option (cond-> {:value (name s)} (= s size) (assoc :selected "")) (label s)])]]
     (if (seq milks)
       [:label " Milk "
        [:select#milk {:data-bind:milk ""}
         (for [m milks]
           [:option (cond-> {:value (name m)}
                      (= m milk)   (assoc :selected "")
                      (sold-out m) (assoc :disabled ""))
            (cond-> (label m) (sold-out m) (str " (sold out)"))])]]
       [:p.muted "No milk"])]))

When the drink changes, the old size or milk may not exist for the new drink. Medium has no meaning for an espresso. valid-choice keeps each value if it's still allowed (and in stock) and otherwise takes the first one that is. The response then carries two events:

(defn drink-options-response
  "Answer a change of drink: new option lists, and new size/milk signals where the old ones
  no longer fit."
  [signals sold-out]
  (let [{:keys [drink size milk]} (->draft signals)
        choice  (valid-choice drink sold-out {:size size :milk milk})
        changed (cond-> {}
                  (not= size (:size choice)) (assoc :size (name (:size choice)))
                  (not= milk (:milk choice)) (assoc :milk (or (some-> (:milk choice) name) "")))]
    (sse/sse-response
     (sse/patch-elements (str (h/html (drink-options-view drink sold-out choice))) {})
     (sse/patch-signals changed {}))))

The first event replaces #drink-options by id, with the chosen options marked selected. The second sets only the signals whose old value no longer fits. Both are needed. The DOM shows the new selection, but the signals are what the next request sends, and a $size still saying "medium" would put a medium espresso in the cart.

The milk-less case is a decision worth looking at. An espresso has no milk, so the obvious patch is {"milk": null}. But a merge patch treats null as "remove this signal". $milk would disappear from the store and from every later payload, and the server would have to treat "missing" and "none" as the same thing. The lesson sends "" instead. The key stays in every request, the value stays a string, and ->draft turns "" into nil on the way in. When nothing needs to change (mocha to mocha, say), changed is empty and the second event is {}, a merge patch that does nothing.

Step through the cases. Each one is the exact response drink-options-response produces.

One more property comes free. If the customer flicks through drinks quickly, several /drink-options requests could be in flight at once, and a slow early response could land after a fast late one. Datastar prevents that by default. With requestCancellation: 'auto', fetch.ts keeps one AbortController per method and URL and aborts the previous request to the same URL when a new one starts. Only the last drink's options are applied.

A searchable variant

The same split works for a combobox with server-side search, which is a good exercise once the lesson passes. The text the customer types is input, so it's a signal, and it must not start with an underscore, because the server needs it. Whether the list is open is presentation, so it's private:

<div data-signals="{query: '', _open: false}">
  <input data-bind:query
         data-on:input__debounce.200ms="@get('/drinks/search')"
         data-on:focus="$_open = true">
  <ul id="drink-results" data-show="$_open"></ul>
</div>

The server filters the menu by query and answers with a patch of #drink-results. Nothing about the menu is sent to the browser except the matching rows as HTML. The __debounce.200ms modifier waits until typing pauses for 200 ms before sending.

What happens when oat sells out

Run the lesson, open two browser windows, and mark oat sold out at the REPL. Nothing changes in either window until someone picks a different drink. The next /drink-options response renders oat as disabled and moves any oat selection to whole. And if a window loaded before the change and its $milk still says oat, add-to-cart refuses it, because the server checks stock on every add. The state is right. The display is stale until the next request.

That's the honest limit of request/response. Part 6 removes it without changing the decision made here: the drop-down stays server-rendered HTML, and the moment Sam marks oat sold out, every open customer page will show it, with no code specific to the drop-down. That only works because the option list was never a signal.

Shared or durable state lives on the server. Anything derived from server data, like an option list, is server-rendered HTML. Uncommitted input is a signal that goes to the server with the command that commits it. Presentation-only state is a _ signal. A drop-down splits across that line: options are HTML, the selected value is a signal, and when the drink changes the server sends both.
