Shaping the backend

A Datastar backend has two kinds of handler: page GETs that return a whole document, and Datastar requests that return patches. Split the second kind into queries and commands, keep the state change in one pure function, and the route table stays small and readable as the app grows.

Parts 1–4 added routes one at a time: /hello, /quote, /drink-options, /cart/items. Each handler read some input, maybe changed the atom, and returned the events for the elements it changed. That works for four routes. Brew Board needs about a dozen, and two kinds of user (Ada at the counter, Sam behind it) who see the same orders. Before we add the rest, it is worth deciding what shape every handler should have. This part decides it. Part 6 then changes one thing about it, and that change is why the shape matters.

Two kinds of request

A browser asks a Datastar backend for things in two different ways, and they need different responses.

A page GET is a normal navigation: the user typed /board or followed a link. There is no Datastar in the request. The browser wants a whole HTML document, so the response is text/html with <!DOCTYPE html>, the Datastar <script type="module"> tag, and the first render of the view. This is also where the sid cookie is set, because it is the first request a new visitor makes.

A Datastar request comes from an action in an attribute: @get('/drink-options'), @post('/orders'). Datastar's fetch.ts sends it with fetch(), not a navigation, so the page stays where it is. Every such request carries the header Datastar-Request: true and Accept: text/event-stream, text/html, application/json, and it carries the signals: as URL-encoded JSON in the datastar query parameter for GET and DELETE, and as a JSON body for POST, PUT and PATCH. The response is a list of patches, usually as an SSE stream.

Inside the second kind, split again by what the request does to the server:

  • Queries read state and return a view of it. They change nothing. They are GETs: GET /drink-options reads $drink and returns the drop-down. A query is safe to repeat, to retry and to prefetch.
  • Commands change state. They are POST, PUT or DELETE: add a line to a cart, place an order, advance an order, toggle a milk. A command is not safe to repeat blindly, and it needs the guard we add below.

This is the same split as CQRS, at the scale of one atom. It costs nothing to adopt and it decides three things for you: the HTTP method, whether the route is guarded, and (in part 6) whether the route returns any HTML at all.

The route table

Parts 1–4 routed with a case on [request-method uri]. That was fine for four fixed paths, but it can't match /orders/:id/advance, and it has nowhere to say "these routes need a guard". The route table has outgrown a case, so this part switches to reitit, where routes are data. Here is Brew Board's table from lesson05.routes, with the two live streams and the native routes left out (they arrive in parts 6 and 7):

(defn app [!state]
  (let [command (fn [f] {:handler f :middleware [wrap-datastar-request]})]
    (ring/ring-handler
      (ring/router
        [["/"                    {:get customer-page}]
         ["/board"               {:get board-page}]
         ["/drink-options"       {:get (partial drink-options !state)}]
         ["/cart/items"          {:post   (command (partial add-item !state))}]
         ["/cart/items/:idx"     {:delete (command remove-item)}]
         ["/orders"              {:post   (command place-order)}]
         ["/orders/:id/advance"  {:post   (command advance-order)}]
         ["/stock/:milk/toggle"  {:post   (command toggle-stock)}]])
      (ring/create-default-handler)
      {:middleware [wrap-params wrap-cookies wrap-sid]})))

Abridged: in the lesson the command handlers are short inline fns that build a command map and call run-command!. command puts the guard into each command route's data, so every command is guarded and no page or query is. (A reitit parent route with :middleware in its data would do the same for a group.)

Read the table top to bottom and you can see the whole app's surface. Three GETs anyone can make. Five commands, all guarded. A command's path names the thing it acts on (/orders/:id) and ends in a verb when the HTTP method isn't enough (/advance, /toggle). Nothing here is Datastar-specific: there is no /api prefix, no JSON endpoints, and no route that exists only to feed a client-side store. Routes return HTML, either a page or patches, and that is the hypermedia part.

Inputs: path, cookie, signals

A Brew Board handler has three places to get input, and each is right for a different thing.

The path names the resource: :id in /orders/:id/advance, :milk in /stock/:milk/toggle. It is visible in logs, it is part of the URL the button calls, and it cannot be changed by typing in a form field.

The cookie says who is asking. wrap-sid reads the sid cookie, or makes a fresh UUID on a page GET and sets it. Ada's cart is (get-in @state [:carts sid]). The browser sends the cookie on every same-origin fetch, so Datastar requests get it without any attribute.

The signals carry what the user typed or chose. Here is the reader, the same function part 3 built:

(defn read-signals [{:keys [request-method query-params body]}]
  (let [raw    (if (#{:get :delete} request-method)
                 (get query-params "datastar")
                 (some-> body slurp))
        parsed (when-not (string/blank? raw)
                 (try (json/parse-string raw true) (catch Exception _ nil)))]
    (if (map? parsed) parsed {})))

Unparseable or non-object JSON gives {}, so a hand-made request reaches validation and gets a message, not a 500. The tests post not json to /cart/items and expect "Pick a drink."

The important fact about signals is the one people get wrong. Datastar does not send "the signals this action uses". The default filter in fetch.ts is include = /.*/, exclude = /(^|\.)_/: it sends every signal on the page whose name has no _-prefixed segment. Try it before reading on.

So a handler must pick the keys it uses and ignore the rest. place-order reads :customer and nothing else. add-item reads :drink :size :milk :qty, and then checks them against the menu and the sold-out set. That check is not optional. Signals are input, as untrusted as a form post, and a user can set any of them from the browser console. Using select-keys plus a validator, as add-to-cart did in part 4, is the habit to keep.

You can narrow what is sent per action, e.g. @post('/orders', {filterSignals: {include: /^customer$/}}). It cuts bytes, and it is worth doing when a page has a large signal you never want on the wire. It is not a security boundary: the server still validates whatever arrives.

A pure core: handle-command

Every command does the same three things: read its inputs from the request, change the state, and respond. Only the middle step is about coffee. Put it in one pure function:

(defn handle-command [state {:keys [type sid line idx customer id milk]}]
  (case type
    :add-to-cart      (cond-> state
                        (nil? (line-error state line)) (update-in [:carts sid] (fnil conj []) line))
    :remove-from-cart (update-in state [:carts sid] drop-index idx)
    :place-order      (let [lines (get-in state [:carts sid])]
                        (if (or (empty? lines) (string/blank? customer))
                          state
                          (-> state
                              (assoc-in [:orders (:next-id state)]
                                        {:id (:next-id state) :sid sid :customer customer
                                         :status :placed :lines lines})
                              (update :next-id inc)
                              (update :carts dissoc sid))))
    :advance          (advance state id)        ;; :placed → :making → :ready → gone
    :toggle-stock     (update state :sold-out #(if (% milk) (disj % milk) (conj % milk)))
    state))

Slightly condensed from lesson05.routes. A command that doesn't apply (an invalid line, an empty cart, an unknown order) returns the state unchanged.

The handler is now thin: turn the request into a command map, then run-command!, which is (command-response (swap! !state handle-command cmd) cmd). A pure function of state and command is easy to test (call it with a map, compare the result) and easy to read, because all of Brew Board's business rules are in one case. It is also the piece that does not change in part 6. Only the response changes.

Validation sits just before the swap, and has a Datastar-specific detail. Datastar applies the body only of a 200 response. In fetch.ts, any other status skips the stream parser: a 204 or a redirect ends quietly, and a 4xx or 5xx fires a datastar-fetch error event and patches nothing (and with the default retry: 'auto', it isn't retried). So "you can't order oat milk, it's sold out" is a 200 whose events patch an error message into the page, as HTML: add-item answers a refused line with <p id="draft-error">Oat milk is sold out.</p> and a good one with the new #cart plus an empty #draft-error. No signal holds the message. A 4xx is for requests no honest page would send.

(defn add-item [!state {:keys [sid] :as req}]
  (let [line (draft-line (sse/read-signals req))]
    (if-let [err (line-error @!state line)]
      (sse/sse-response (sse/patch-elements (html [:p#draft-error err])))
      (update (run-command! !state {:type :add-to-cart :sid sid :line line})
              :body str (sse/patch-elements (html [:p#draft-error]))))))

Responding: fragment per action

In this part each command answers with the patches for what it changed. That is command-response: given the new state and the command, return the response. For add-to-cart that means the new #cart. For place-order it means the empty #cart, the new entry in #my-orders, and a patch-signals that clears $customer:

HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache

event: datastar-patch-elements
data: elements <section id="cart">…<p class="muted">Empty.</p>…</section>

event: datastar-patch-elements
data: elements <section id="my-orders"><h2>Your orders</h2><ul><li>#1 for Ada: placed</li></ul></section>

event: datastar-patch-signals
data: signals {"customer":""}

Tip. When the server re-renders an element anyway, let it decide disabled too. cart-view renders "Place order" with disabled while the cart is empty, and every cart command re-sends #cart, so the button is always right. A client expression such as data-attr:disabled="$cartCount == 0" would need a count signal that mirrors server state.

It is the natural first design, and the one you'd write coming from htmx. It also has a cost that grows with the app: each command has to know which parts of which pages show the thing it changed. place-order knows about #cart and #my-orders. When you add an order count to the header, you must remember to add it to place-order's response, and to advance-order's, and to every other command that changes orders. Forget one and that view is stale until a reload.

And there is a worse gap. The response goes to the browser that sent the request. Sam has /board open in another browser. What does Sam see when Ada orders?

The second mode in the figure is where part 6 goes. Commands answer 204 No Content and do nothing but swap!. Every open page holds one long-lived GET, and when the atom changes, the server renders each page's whole view again and sends it down that stream. No command knows about any view, and every viewer is current. It sounds expensive and it sounds like it would wreck focus and typed text. Part 6 shows why it does neither.

Guarding commands

A command changes state using the caller's cookie, so it is a CSRF target: a page on evil.example could make Ada's browser post to /orders, and the browser would attach Ada's cookie. Brew Board uses a cheap guard:

(defn wrap-datastar-request [handler]
  (fn [req]
    (if (= "true" (get-in req [:headers "datastar-request"]))
      (handler req)
      {:status 403 :headers {"Content-Type" "text/plain"} :body "Datastar requests only"})))

Why this helps: a plain HTML form on another site can POST cross-origin, but it cannot set a custom header. A cross-origin fetch that sets Datastar-Request is not a "simple request", so the browser first sends a CORS preflight, and our server does not answer preflights with permission, so the real request is never sent. (Ring lowercases header names, hence "datastar-request".)

Be precise about what this is. It is a partial defense. It relies on the server never adding permissive CORS headers, and it is best paired with SameSite=Lax (or Strict) on the session cookie, which stops the browser attaching the cookie to cross-site POSTs at all. A real app adds a CSRF token as well: render it into a signal on the page GET (for instance data-signals:csrf, not _-prefixed, because it has to be sent), and check it in this same middleware. The toy stops at the header.

Expressions are JavaScript

The board renders one button per order, with the order's id inside the expression: (str "@post('/orders/" id "/advance')"). That is safe because id is an integer the server assigned. Now suppose a "reorder" button carried the customer's name the same way:

;; WRONG: a stored value inside an expression
[:button {:data-on:click (str "@post('/orders?for=" customer "')")} "Reorder"]

A customer who typed their name as x');alert(1);(' gets this HTML:

<button data-on:click="@post(&apos;/orders?for=x&apos;);alert(1);(&apos;&apos;)">

Hiccup escaped every quote, and it didn't help. Escaping protects the HTML attribute: the browser decodes &apos; back to ' when it parses the page, and Datastar reads the decoded value from el.dataset (applyEls in engine.ts). What Datastar evaluates is @post('/orders?for=x');alert(1);(''), three JavaScript statements, the second of them chosen by the customer. That is stored XSS, and it fires for whoever clicks Sam's button.

The rule: put only three kinds of thing inside an expression string.

  • Server literals: an integer id, a keyword from a fixed set ((name milk) for :oat), true/false.
  • URL-encoded values: (ring.util.codec/url-encode customer) turns x');alert(1);(' into x%27%29%3Balert%281%29%3B%28%27, which can't end the string.
  • Signal references: @post('/orders') and let $customer travel in the body, or refer to an id the server owns and look the name up there.

Never a raw stored or request value. The same thinking covers the other two places values meet code. Seed signals with cheshire ({:data-signals (json/generate-string m)}): JSON is a JavaScript literal and cheshire escapes the quotes inside strings, which hand-built (str "{name: '" name "'}") doesn't. And inline <script> text must escape </, or a value containing </script> ends the tag; part 7's bridge-script does this.

htmx marks its requests with HX-Request: true and expects HTML fragments back, swapped by hx-target/hx-swap attributes on the client. Datastar puts the target in the response: the element's id, or a selector and mode in the event. That moves "which part of the page does this update?" from markup to the server, which is what makes part 6's whole-view render possible.

What a good route table looks like

  • Few GETs, no "data" endpoints. Pages, and queries that return patches. If you find yourself writing GET /api/orders returning JSON for the page to render, you are rebuilding the SPA. Render the HTML on the server.
  • Commands are named for intent. POST /orders/:id/advance, not PUT /orders/:id with a status field. The server decides what "advance" means; the client can't send :status :picked-up and skip :making.
  • One pure state function. Handlers translate HTTP to commands. Rules live in handle-command.
  • The guard is route data, applied to the command group, so a new command can't forget it.
  • Responses are patches, and (from part 6) mostly not even that.

Pages are GETs that return documents. Datastar requests split into queries (GET, change nothing) and commands (POST/PUT/DELETE, guarded, change state through one pure handle-command). Signals arrive all at once, so pick the keys you use and validate them. Answering each command with the patches it caused works, but only for the browser that asked. That gap is what part 6 closes.
